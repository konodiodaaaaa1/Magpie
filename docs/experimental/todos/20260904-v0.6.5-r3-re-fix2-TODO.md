# v0.6.5 r3 re fix2 TODO：恢复工具栏式的同帧浮窗呈现

基线：`0.6.5` 分支上的 v0.6.5 r3 re fix1 工作树，HEAD 为 `84d9f6abb8203a79f9a44d9a66984a293e68856d`。

本文只记录下一轮执行方案，不修改产品代码、不构建、不部署。

## 问题结论

- r3 re fix1 调整了输入到 ImGui DrawData 的更新频率，但没有改变 DrawData 到实际前端 Present 的等待路径，因此可以对用户观察到的浮窗呈现延迟完全无效。
- 当前工具栏与参数浮窗并没有两套 Presenter。`_DrawToolbar` 和 `_DrawEffectParameters` 在同一次 CPU UI frame 中执行，最终进入同一个 ImGui DrawData、同一个 `_FrontendRender` 和同一次 Present。
- 可参考的不是“工具栏专用 Present API”，而是 r3 以前工具栏使用的完整生命周期：前端确定本轮要呈现并取得 back buffer 后，才执行 `ImGui::NewFrame -> 生成 UI -> ImGui::Render -> GPU Draw -> Present`。
- 当前 r3 re 将 UI 拆成提前执行的 `OverlayDrawer::Update` 和稍后执行的 `OverlayDrawer::Draw`，并增加 `_updatePending`、`_visualDirty`、DrawData ready 以及 8/16 ms 门控。它让 UI 状态和真正提交的前端帧成为两个时刻。
- 最新人工测试日志使用普通 DLSSNR 路径，没有启用 DLSSFG 或 XeSSFG；当前现象不能归因于 DLSSFG FIFO 或 XeSSFG 的真实输入帧限制。

## fix2 目标

- 参数浮窗和工具栏统一恢复为“确定 Present 后，在同一个前端帧内生成并绘制”的模式。
- 鼠标移动时，参数滑条、窗口移动、滚动和 resize grip 与软件光标在同一次可见帧中更新。
- 输入处理仍不在 WndProc 中执行 GPU 工作。
- down/up 边沿保持有序且分别获得 UI 推进机会，不能为了降低呈现延迟重新引入粘键或无法释放。
- UI 控件反馈与后台效果结果分成两条链路验收；后台效果稍后生效不得阻塞浮窗自身呈现。

## A. 移除 r3 re fix1 的无效刷新层

- [x] 删除 `OVERLAY_IDLE_INTERVAL`、`OVERLAY_INTERACTION_INTERVAL` 及浮窗自身的 8/16 ms Present 门控。
- [x] 删除 `_lastUiFrameTime`、`_highFrequencyRedraw` 和只为预生成 DrawData 服务的调度状态。
- [x] 删除 `Renderer::MessageHandler` 中输入前后的强制 `OverlayDrawer::Update`；WndProc 只记录输入和脏状态。
- [x] 重新评估并删除 `_updatePending`、`_visualDirty`、`_drawDataReady`、`_pointerMotionPending` 中不再必要的字段，最终只保留一个不承载输入边沿的 `overlayDirty`。
- [x] 不保留“把 16 ms 改成 8 ms”或根据 ActiveID 动态调间隔的补丁；刷新速率由统一前端调度和 Presenter 容量决定。

## B. 恢复工具栏原始的同帧生成与绘制

- [x] 将 `OverlayDrawer::Update + OverlayDrawer::Draw` 收敛回一次前端调用；该调用在同一栈内完成 `NewFrame`、工具栏、Profiler、参数窗口、`ImGui::Render` 和 backend DrawData 绘制。
- [x] `_FrontendRender` 必须先通过 `Presenter::BeginFrame` 并取得有效 back buffer，再调用 Overlay UI frame；完成后紧接着绘制软件光标并执行 `EndFrame/Present`。
- [x] 工具栏和参数浮窗必须共用同一个 ImGui frame、DrawData 和 Present，不增加参数浮窗专用 swap chain、DComp visual 或 overlay-only Presenter。
- [x] 浮窗隐藏时仍能在下一次统一前端帧清除旧像素；不得依靠保留过期 DrawData 完成擦除。
- [x] Profiler timings 只在真实后端新帧到达时采样，cursor/overlay-only 前端帧不得重复累计同一个样本。

目标链路：

```text
OS input/state change
  -> queue ImGui input + overlayDirty
  -> normal frontend scheduler
  -> Presenter::BeginFrame
  -> OverlayDrawer frame
       ImGui::NewFrame
       Draw toolbar + profiler + effect parameters
       ImGui::Render
       GPU draw ImGui DrawData
  -> CursorDrawer::Draw
  -> Presenter::EndFrame / Present
```

## C. 统一前端脏状态

- [x] `newBackendFrame`、`cursorDirty`、`overlayDirty` 三者任一成立即可请求同一条 `_FrontendRender`；不得互相调用或建立从光标到浮窗的反向依赖。
- [x] 鼠标移动只保留最新坐标；其可见刷新自然复用 `cursorDirty` 触发的前端帧。
- [x] 光标位置不变的 down/up、wheel、窗口关闭、状态文字和透明度变化必须设置 `overlayDirty`，不得依赖 `CursorDrawer::NeedRedraw()`。
- [x] 输入产生的 `overlayDirty` 在成功提交包含该 UI frame 的 Present 后才清除；`BeginFrame` 或 `EndFrame` 失败时继续保留。
- [x] 静态源上也必须允许 cursor/overlay-only 前端帧复用最后一张已发布的底图，不等待新的捕获帧。

## D. 保证 button edge 与 Present 顺序

- [x] WndProc 不直接调用 `Renderer::Render`、`BeginFrame`、`EndFrame`、DWM wait 或 GPU fence。
- [x] 消息泵允许合并连续 move，但遇到 Overlay-owned button down/up 或 wheel 后结束当前消息批次，立即回到外层正常前端 Render。
- [x] down 和匹配的 up 不得在同一次消息批次中被一起吞并；每个边沿至少有一次 ImGui frame 推进机会。
- [x] button-up 即使发生在浮窗外、浮窗关闭后或 `WantCaptureMouse` 已改变，也必须结束已有 Overlay ownership。
- [x] 不恢复 `SetCapture`、`GetAsyncKeyState` reconcile、焦点 cancel、固定 settle frame 或多状态按键机。
- [x] move 合并只覆盖坐标快照，不合并、重排或推测 button/wheel 边沿。

## E. 分离 UI 呈现和实时效果应用

- [x] Slider/Checkbox 的控件视觉结果先通过最近一次正常前端 Present 显示，不等待 backend 参数邮箱。
- [x] Live 参数继续经 last-write-wins mailbox 投递到 backend thread；成功应用后单独触发包含新效果底图的前端帧。
- [x] 不让 backend shader、DLSSNR evaluate 或 Frame Guidance 执行阻塞 ImGui 状态生成；共享纹理同步仍属于统一前端 Present 的既有底图复制边界。
- [ ] 分别记录两项延迟：`input -> UI Present` 和 `input -> updated effect texture Present`，禁止用后一项判断浮窗本身是否跟手。
- [x] RestartRequired 参数只更新草稿和 UI，不应触发 backend render。

## F. Presenter 边界

- [x] 普通 AdaptivePresenter：cursor/overlay dirty 应直接复用最后一张底图提交，不等待捕获源产生新帧。
- [x] DLSSFG：继续由既有 FIFO 保持生成帧顺序；Overlay 在下一张合法 FIFO 前端帧中同帧生成和绘制，不创建旁路消费者。
- [x] XeSSFG：保留 SDK 对真实颜色输入帧的约束，并明确其 UI 可见延迟上限；不得把 overlay-only 帧伪装成新的 XeSSFG 输入帧。
- [x] 调整大小期间继续走 Presenter 已有的 DComp/resize 路径，但 Overlay UI 仍只在实际提交的前端帧内生成一次。

## G. 验收与诊断

- [ ] 普通静态源上分别操作工具栏按钮、参数 Slider、Checkbox、滚动条、窗口拖动和右下角 resize grip；两类窗口的视觉延迟应一致。
- [ ] 录制或记录 `input sequence/time -> ImGui frame -> BeginFrame -> overlay draw -> EndFrame`，确认一次交互不存在额外 8/16 ms Overlay 门控。
- [ ] 快速移动后立即按下、快速 down/up、拖出窗口释放、左右键交错均不得粘键。
- [ ] UI 控件已移动但效果尚未更新时，应能从诊断中明确归类为 backend apply 延迟，而不是 Overlay Present 延迟。
- [ ] 普通动态源、普通静态源、DLSSFG x2/x3/x4 与 XeSSFG 分别回归；至少记录显示刷新率、Presenter 类型和 input-to-present 时间。
- [x] Release x64 构建、`git diff --check` 和包体审计通过后，覆盖部署到 `v0.6.5-r3-local`。

## 建议执行顺序

1. 移除 fix1 的 Overlay 计时器和 CPU/GPU DrawData 分离状态。
2. 将完整 ImGui frame 移回 `_FrontendRender`，参数窗与工具栏一起生成并绘制。
3. 将 Renderer 门控收敛为 `backend || cursor || overlay` 三个脏原因。
4. 在消息泵中以 button/wheel edge 结束批次，保证边沿分别推进，move 保持合并。
5. 为普通 Presenter 增加短期 input/UI/effect 三段时间诊断并完成静态源人工测试。
6. 回归 DLSSFG/XeSSFG 的顺序约束后全量构建并覆盖部署。

## 完成定义

- 工具栏与参数浮窗不再存在不同或分阶段的 UI 呈现生命周期。
- 每个实际提交的前端帧使用本帧生成的 ImGui DrawData，不绘制提前冻结并等待的浮窗状态。
- 鼠标移动时浮窗与软件光标在同一 Present 中出现；光标静止时其他浮窗状态仍可独立请求 Present。
- down/up 的正确性不依赖刷新率、后台捕获帧率或兼容性轮询。
- UI 呈现延迟和效果应用延迟可被独立测量、独立判断。

## 执行结果

- 已删除 r3 re fix1 的提前 DrawData、8/16 ms Overlay 计时器以及输入前后的强制 `OverlayDrawer::Update`。
- `OverlayDrawer::Draw` 现仅在 `_FrontendRender` 成功取得 back buffer 后执行，并在同一调用栈完成 ImGui frame、工具栏、Profiler、参数窗口、GPU DrawData、软件光标和 Present。
- 普通路径的提交条件已收敛为后端新帧、光标变化或 `overlayDirty`；失败的 `BeginFrame` 不消费 dirty，失败的 `EndFrame` 会恢复 dirty。
- Overlay-owned down/up/wheel 会在 WndProc 返回后终止当前消息批次，并由缩放线程外层立即调用正常 Render；连续 move 仍只在下一帧采样最新 `CursorManager` 坐标。
- DLSSFG 仍只消费既有 FIFO，且新增每个共享槽位的 generated/real 标记，Profiler 不再把 generated FIFO 帧当作新的真实后端效果采样；XeSSFG 仍禁止 overlay-only 伪输入帧。
- Release x64 完整 Rebuild 已通过并覆盖 `v0.6.5-r3-local`。部署目录和 ZIP 均为 236 个文件；EXE SHA-256 为 `6DC7A664765D5C521F0A675B2A4570298309872438615175194B0F883E088019`，ZIP SHA-256 为 `9FEDEC4DE7AEFA78BC5BE7171D965F7D6E975B3C980C648454885F57A095B525`。
- 包体审计未发现 cache、logs、PDB、LIB、EXP、深度估算、ONNX Runtime 或 TensorRT 残留。
- G 节未勾选项目仍需在目标 GPU 上人工完成，尤其是静态源、快速 down/up、拖出释放、DLSSFG x2/x3/x4 与 XeSSFG 的 input-to-present 对比。
