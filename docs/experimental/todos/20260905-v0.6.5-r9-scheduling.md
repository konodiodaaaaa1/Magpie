## 捕获交付

原实现通过 `Direct3D11CaptureFramePool::Create` 的消息派发让后端醒来。改用 `CreateFreeThreaded`，WGC 内部工作线程的回调仅设置本会话事件；所有取帧、纹理复制与效果处理继续由后端线程执行。[Microsoft API 说明](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded?view=winrt-26100)

- `StepTimer` 同时等待到帧事件和线程消息；第一帧、普通等待和最小帧率等待都可由到帧信号唤醒。退出、参数更新等控制消息仍能打断等待。[Microsoft 等待函数说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-msgwaitformultipleobjectsex)
- 等待最大帧率截止时间时不监听持续置位的到帧事件，避免快速源绕过限帧或造成空转。
- 使用手动复位事件，在读取帧池前复位。取帧过程中或最后一次取帧之后到达的通知继续保持置位，避免清掉下一张帧的唤醒。
- 每次最多取出 4 张并保留最新张，保持原有延迟策略。本次没有直接缩小帧池。
- 每个捕获会话独立持有信号状态；回调捕获该状态的共享所有权，不捕获 `this` 或 D3D 上下文。先注销回调再关闭会话／帧池；晚到的旧回调只能触碰旧信号，不能唤醒新会话或访问已析构对象。
- 原有内容范围、时间戳、历史序列和五秒异常恢复规则保持。本次没有把普通静态画面无新帧当作错误。

诊断构建另加 `WgcNotificationWait`、`WgcDequeue`、`CaptureWake` 事件，用于后续区分通知等待和池内跳帧；正常构建中通知回调不读取诊断时钟，也不更新诊断原子计数。

## 呈现与 GPU 调度

- 主循环先处理已发布的新内容／DLSSFG FIFO，再处理仅叠加层重绘。一次调度循环最多发起一次窗口渲染尝试，避免先提交旧底图、紧接着再提交新内容。
- 普通帧通知也会在处理叠加层输入前被读取，减少高频鼠标输入让已到达内容滞留消息队列的机会。
- 仅叠加层重绘按目标显示器刷新率合并；成功提交新内容且 UI 同层时，也更新叠加层截止时间。提交失败不会推进该时钟。
- 鼠标连续移动和拖动保留最新位置，按钮按下／松开、滚轮、取消及显式工具栏动作可立即呈现。输入队列原有按钮边界和成功呈现后的确认规则保留。
- 工具栏动作采用接收／已呈现序号；绘制过程中触发的新动作不会被当前帧误确认。主循环读取帧通知时也检查 `WM_QUIT`，确保退出不会被筛选读取吞掉。
- 周期检查间隔取显示周期和 8 ms 中较小者；内容／输入消息可提前唤醒，已到达但暂未能呈现的内容仍短间隔重试。
- 独立叠加层中的原图对比、依赖背景的光标跟随新内容更新，不受纯叠加层限频影响。DLSSFG 的帧序、槽释放和目标截止时间逻辑保持。
- 按用户最后明确要求，GPU 调度类保持 REALTIME；设置函数恢复为修改前的实现。此次通过减少多余呈现工作优化开销，不调整 GPU／CPU 优先级。

正常日志在会话开始记录捕获通知模式和叠加层目标间隔；没有添加新的界面提示或用户配置项。

## 验证与实际限制

本次使用 Release x64 正常构建，MSBuild `/m:4`，跨项目最多 16 个编译任务，沿用用户允许提高的并发。

CPU 检查链接本次编译出的 `Magpie.Core.lib`，实际调用 `StepTimer`，没有创建窗口、捕获设备或启动 Magpie：

- 已经置位的到帧事件可直接通过首次等待。
- 新到帧事件和控制消息分别在约 18 ms、16 ms 后唤醒等待，没有等到 500 ms 轮询超时。
- 新帧可中断最小帧率的定时等待；持续置位的帧事件不能绕过最大帧率截止时间。
- 叠加层首次呈现、刷新周期、关键输入立即响应、失败／尚未到期不推进时钟、长停顿后无追赶突发、无效刷新率回退通过。
- FG 采样仍排除下游等待时间，200 ms 的下游停顿不会持续拉长恢复后的补帧间隔。

测试代码及构建记录在工作区 `.tools/r9-optimization/`。图像正确性、切屏／捕获重启、鼠标拖动、DLSSFG／XeSSFG 和实际 1% Low 由用户测试。本次是针对证据的优化，不能将编译或 CPU 检查通过当作严重卡顿已完全修复。
