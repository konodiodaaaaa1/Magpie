# v0.6.5 r3 re fix4 TODO：输入缓冲、最高优先级调度与低帧率 UI 呈现解耦

基线：`0.6.5` 分支上的 v0.6.5 r3 re fix2 工作树，HEAD 为 `84d9f6abb8203a79f9a44d9a66984a293e68856d`，当前本地部署版本为 `v0.6.5-r3-local`。

本文只整理问题结论和下一轮执行清单；本轮不修改产品代码、不构建、不部署。

## 用户反馈

- 捕获内容更新较慢或完全静止时，例如视频暂停，工具栏和参数浮窗的视觉更新明显变慢或停止。
- 即使缩放窗口已经收到鼠标消息，浮窗移动、窗口 resize、Slider、滚动条和工具栏按钮仍可能很久以后才产生新的可见 Present，严重时表现为无法点击。
- 用户输入应高于捕获帧、帧生成 FIFO 和普通重绘通知：一旦收到输入，应停止继续处理低优先级帧任务，并尽快生成和提交包含最新输入状态的 UI 帧。
- 建议所有输入先进入应用层缓冲区，在真正准备生成 UI 的最晚时刻合并成有序事件批次，再传入 ImGui。

## 调查结论

### 1. 当前“收到输入”不等于 ImGui 已经处理输入

- `ImGuiImpl::MessageHandler` 当前会立即调用 `io.AddMouseButtonEvent` / `io.AddMouseWheelEvent`，但这些调用只把事件加入 ImGui 内部队列。
- 点击、ActiveID、Slider 数值、窗口移动和 resize grip 只有执行下一次 `ImGui::NewFrame` 后才会真正推进。
- r3 re fix2 把 `ImGui::NewFrame` 放在 `_FrontendRender` 成功取得 back buffer 之后。若 Presenter 不允许本轮呈现，或前端线程阻塞在 pacing、frame-latency wait、keyed mutex 等位置，输入虽已收到，却没有得到 UI frame。
- 因此当前问题不是缺少 `overlayDirty`，而是输入消费与可见 Present 仍依赖同一个可能被拒绝或阻塞的前端路径。

### 2. 当前“输入边沿立即 Render”不是真正的最高优先级

- button down/up 和 wheel 只会设置 `_overlayInputEdgePending`，让外层消息循环结束当前批次后调用一次 `ScalingWindow::Render()`。
- DLSSFG 同步模式会直接拒绝普通 `Renderer::Render()`；XeSSFG 没有新真实后端帧时也会拒绝 overlay/cursor-only Present，因此这次“立即 Render”可以只是一次返回 `false` 的空操作。
- `WM_MOUSEMOVE` 只标记 redraw，不会像 button/wheel edge 一样立即结束消息批次；浮窗、Slider 和 resize grip 的连续拖动仍可能排在帧消息之后。
- `MAX_MESSAGES_PER_PASS` 只能限制每轮分发数量，不能中断已经开始的 DLSSFG pacing、Presenter wait、纹理同步或 Present。

### 3. 前端帧工作放在窗口线程内，输入无法抢占正在执行的等待

- 缩放线程同时负责 Win32 消息分发、ImGui、光标、前端纹理复制、Presenter 等待和 Present。
- `WM_FRONTEND_RENDER_DLSSFG` 当前在 WndProc 调用栈内完整执行 `RenderDLSSFGFrame`，包含 pacing、`BeginFrame`、Overlay Draw 和 `EndFrame`。
- `AdaptivePresenter::BeginFrame` 和 `XeSSFGPresenter::BeginFrame` 最长可等待 1000 ms；前端共享纹理仍有 `AcquireSync(..., INFINITE)`。
- 线程一旦进入这些阻塞调用，后续鼠标消息无法被分发；已分发的鼠标事件也只能等待调用返回后才能进入下一次 ImGui frame。
- “中断”应定义为：停止继续调度尚未开始的帧任务，并唤醒可取消的 pacing/capacity wait；不得尝试取消已经提交给 DXGI、DWM 或 FG SDK 的 Present。

### 4. 低帧率/静态源下，三类 Presenter 的行为不同

| 模式 | 没有新捕获内容时的当前行为 | fix4 要求 |
| --- | --- | --- |
| 普通 Presenter | 理论上可复用最后一张后端纹理，但仍可能受同线程等待和纹理同步影响 | 输入可立即请求复合最后底图并 Present |
| DLSSFG | 普通 Render 被拒绝，只能等待下一张合法 FIFO 输出帧 | UI 不得依赖下一张 FG FIFO；也不得破坏 generated/real 顺序或抢占活动 ring slot |
| XeSSFG | 明确抑制没有新真实捕获帧的 overlay-only proxy Present | UI 必须与 XeSSFG 游戏颜色输入分层，不能把 UI 更新伪装成新的 SDK 输入帧 |

### 5. 应用层输入缓冲可行，但不能压缩为“最终状态”

- 连续 move 可以 last-write-wins；button down/up/cancel 必须无损、保序且携带事件发生时的位置。
- 不得把同一次快速点击合并为最终 `button=false`，否则 ImGui 看不到点击；也不得把 Down 前、拖动中、Up 后的所有位置合并成一个最终坐标。
- ImGui 的 trickle queue 可能把同一批次的 down/up 分配到多个 `NewFrame`。应用层不能把全部边沿一次性交给 ImGui 后立即认为输入已消费完成。
- 缓冲区应保留尚未交付的有序边沿，并为每个实际 UI frame 提交一个连续、可验证的事件片段；只在成功 Present 后确认该 UI 状态已经可见。

## fix4 目标与边界

- 建立一条统一输入链：`Win32 input -> PendingInputBuffer -> ImGui frame -> DrawData -> Present acknowledgement`。
- button down/up/wheel/cancel 为无损最高优先级；拖动期间的 move 为可合并最高优先级；普通 hover move 可合并为较低优先级。
- 在所有可能阻塞的 frame-capacity/pacing/底图同步完成之后、紧邻 `ImGui::NewFrame` 的位置注入最新输入快照。
- 普通、DLSSFG 和 XeSSFG 共用同一输入缓冲、所有权和确认模型；只允许 UI 的最终合成/呈现策略不同。
- UI 响应不依赖捕获内容帧率、duplicate-frame detection、FG multiplier 或 FrameRate Filter。
- 不再加入 fixed settle frame、8/16 ms Overlay timer、`GetAsyncKeyState` reconcile、焦点轮询或更多互相校正的布尔补丁。
- 不改变效果算法、参数语义、Live/RestartRequired 分类、DLSSFG generated/real 顺序或 XeSSFG SDK 输入合同。

## A. 建立应用层 PendingInputBuffer

### A1. 定义最小事件模型

- [ ] `ImGuiImpl::MessageHandler` 不再直接调用 `io.AddMouse*Event`；WndProc 只做坐标快照、命中/所有权判定、事件入缓冲和 urgent 标记。
- [ ] 定义有界 `PendingInputEvent`：单调递增 sequence、事件类型、button、down/up/cancel、事件坐标、wheel delta、目标/所有权和必要的窗口几何 generation。
- [ ] 分离“有序边沿队列”和“最新连续状态”：button/cancel 使用 deque；move 使用 latest snapshot；wheel 使用相邻可累积 delta。
- [ ] 对 L/R/M/X1/X2 使用一个 ownership bitmask；某按键由 Overlay 接收 Down 后，配对 Up/Cancel 无条件进入同一队列，不再由后续 hover 或 `WantCaptureMouse` 决定是否丢弃。
- [ ] Down 的路由基于用户实际看到的最后一次成功 Present 的窗口矩形；记录目标窗口/Overlay ownership，避免延迟消费时使用已经变化的布局重新命中。
- [ ] 缓冲区设明确上限；move/wheel 优先合并，绝不丢 Up/Cancel。若不可恢复地溢出，执行一次带诊断的统一 cancel，不静默覆盖边沿。

### A2. 明确合并规则

- [ ] 连续 `Move(A), Move(B)` 合并为 `Move(B)`。
- [ ] `Move(B), Down(C), Move(D), Move(E), Up(F), Move(G)` 只能合并为 `Move(B), Down(C), Move(E), Up(F), Move(G)`；禁止跨 Down/Up 合并位置。
- [ ] 每个 Down/Up/Cancel 前先向 ImGui 提交该边沿绑定的位置，确保点击、拖动距离和 resize 命中使用事件时坐标。
- [ ] 相邻同方向 wheel 可以累积；遇到 button edge、cancel、leave 或目标变化时先封包，不能跨控制边沿累积。
- [ ] `WM_MOUSELEAVE`、`WM_CAPTURECHANGED`、`WM_CANCELMODE`、窗口销毁和缩放结束不可被普通 move 覆盖；它们进入统一 cancel/leave 事务。
- [ ] 不在 WndProc 里调用 `ImGui::NewFrame`、`ImGui::Render`、Renderer、Presenter、GPU fence、DWM wait 或效果参数应用。

### A3. 输入序号与确认语义

- [ ] 维护 `receivedSerial`：应用层已收到的最新输入 sequence。
- [ ] 维护 `consumedSerial`：已经提交给某次 ImGui frame 的最大 sequence。
- [ ] 维护 `presentedSerial`：包含对应 UI 状态的前端帧已经成功提交的最大 sequence。
- [ ] 只有 `EndFrame/Present` 成功后才推进 `presentedSerial`；`BeginFrame` 失败、底图同步失败或 `EndFrame` 失败时不得确认该批输入已经可见。
- [ ] 若生成本帧快照后又收到更新，`receivedSerial > consumedSerial/presentedSerial` 必须继续保持 urgent/dirty，不能被本帧清除。

## B. 在最接近 Present 的位置向 ImGui 注入

### B1. 拆分“等待呈现机会”和“生成 UI”

- [ ] 将 Presenter 容量等待、FG pacing、共享底图同步与 ImGui frame 生成分成可测量阶段；禁止在长等待前冻结一份输入快照。
- [ ] 普通路径在取得可写 back buffer、完成最后底图复制后，立即从 `PendingInputBuffer` 取得快照，再执行 `io.AddMouse*Event -> ImGui::NewFrame -> UI build -> ImGui::Render`。
- [ ] 快照后到 `ImGui::NewFrame` 之间不得执行可能长时间等待的 GPU/SDK 操作。
- [ ] 若当前窗口线程仍负责消息接收，Presenter 的容量等待必须非阻塞或可被 input event 唤醒；不能在阻塞一秒后才读取“最新”缓冲区。
- [ ] 不在渲染中通过通用 `PeekMessage/DispatchMessage` 重入整个 WndProc；如需专用输入线程，只允许该线程生产缓冲事件，ImGui 始终由一个消费线程拥有。

### B2. 逐片段交付边沿

- [ ] 每次 UI frame 从缓冲区取一个连续事件片段；不得无条件把积压的全部 Down/Up 一次性倾倒进 ImGui 后清空应用层队列。
- [ ] 核实当前 ImGui 版本的 `ConfigInputTrickleEventQueue` 行为；若快速 down/up 需要多个 `NewFrame`，根据明确的剩余边沿继续调度，而不是固定补两帧。
- [ ] 一个边沿片段已交给 ImGui、但对应 UI frame 未成功 Present 时，保留“已消费、未呈现”状态；不得重复触发 click action，也不得提前丢掉视觉更新请求。
- [ ] 连续拖动每个显示周期最多提交一次最新位置，避免 1000 Hz 鼠标为每条 move 建立一张 UI 帧；释放边沿不受该限速影响。

## C. 建立真正的输入最高优先级调度

### C1. WndProc 只生产输入，外层 Scheduler 决定工作顺序

- [ ] 删除 `overlayInputEdgePending -> 立即调用一次可能返回 false 的 Render` 这种伪优先路径，改为一个可观察的 `urgentInputGeneration`/event。
- [ ] 消息泵每次开始捕获/FIFO/普通重绘任务前先处理 input/control；发现新 button/wheel/cancel 或活动拖动 move 后立即停止继续分发低优先级帧消息。
- [ ] `WM_FRONTEND_RENDER` 继续允许合并；`WM_FRONTEND_RENDER_DLSSFG` 保持 FIFO 顺序，但不得在 WndProc 内执行完整阻塞式 Present。
- [ ] 将 DLSSFG FIFO 消息转换为 Scheduler 的有序 frame job；输入可以在两个 job 之间抢占，但不能重排 generated/real frame，也不能中断已经提交的单帧 Present。
- [ ] quit、设备丢失、窗口销毁和统一 cancel 与 button-up 同级，始终先于新帧任务。

### C2. 让等待可被输入唤醒

- [ ] 将 DLSSFG deadline/DWM pacing 改为可等待“deadline 或 urgent input/control”的机制；输入到达时先返回 Scheduler，而不是继续睡到目标时间。
- [ ] 将 swap-chain frame-latency wait 从 1000 ms 单次阻塞改为非阻塞容量查询或可中断等待；不得通过忙轮询提高 CPU 占用。
- [ ] 重新设计前端 keyed-mutex 获取，移除 UI/窗口线程上的 `AcquireSync(..., INFINITE)`；使用有界等待、稳定底图缓存或异步复制，失败时保留输入 dirty 并重试。
- [ ] 已进入不可取消的 DXGI/DWM/SDK 提交后不强制打断；只保证返回 Scheduler 后输入必定先于下一项 frame job。

### C3. 优先级分级

- [ ] P0：button up/down、wheel、cancel/capture loss、quit/device loss。
- [ ] P1：ActiveID/窗口拖动/resize grip/Slider/滚动条交互期间的最新 move。
- [ ] P2：普通 hover move、tooltip、toolbar alpha 和状态文字更新。
- [ ] P3：捕获通知、普通 redraw、DLSSFG 下一 FIFO frame；DLSSFG 内部相对顺序保持不变。
- [ ] 优先级只决定尚未开始的任务顺序，不改变同类输入事件的 sequence，不允许 P1 move 越过 P0 Down/Up。

## D. 解除 UI Present 对捕获帧率的依赖

### D1. 普通 Presenter

- [ ] 保存一份由前端拥有、已完成同步的最后显示底图；overlay/cursor-only 帧直接复合该缓存，不重复争用正在由 backend 写入的共享槽位。
- [ ] 输入到达且已有有效底图后，即使捕获源 `Waiting`，也允许生成并提交 UI 帧。
- [ ] 第一张有效捕获帧前不读取未初始化底图；只保留输入，首帧到达后立即按最新状态呈现。

### D2. DLSSFG

- [ ] DLSSFG generated/real FIFO 继续是后端颜色帧的唯一有序消费者；UI-only 呈现不得占用、释放或复用仍由 ring 管理的活动槽位。
- [ ] 每次合法 FIFO 帧显示后，将最终无 Overlay 的稳定颜色底图或等价前端副本保存到 UI 合成缓存。
- [ ] 后续只有输入变化时，以该稳定底图生成 UI 帧，不调用 DLSS Frame Generator，不增加 captured frameId，不制造 generated/real 假帧。
- [ ] UI 抢占只延后尚未开始的下一张 FIFO Present；不得跳过 FIFO、改变 multiplier 或让后端 ring 无界增长。

### D3. XeSSFG

- [ ] 不通过 XeSSFG proxy swap-chain 的额外 Present 显示 UI，因为这会把相同颜色帧计为新的 SDK 输入。
- [ ] 评估并实现位于 XeSSFG 内容之上的独立 DirectComposition UI visual/surface；工具栏、参数浮窗和软件光标在该层按输入独立更新。
- [ ] UI layer 的尺寸、DPI、裁剪、黑边、窗口移动/resize 和可见性与底层 XeSSFG visual 保持原子同步。
- [ ] 若平台无法安全建立独立 UI layer，必须明确降级策略和能力提示；禁止静默回到“等待下一张真实捕获帧才响应点击”。

## E. 所有权、释放和生命周期

- [ ] Overlay-owned Down 建立一次所有权；所有后续 move/up/cancel 都根据该所有权路由，不依赖延迟的 `io.WantCaptureMouse`。
- [ ] Up 到达时立即结束应用层所有权和 CursorManager capture；视觉确认可以稍后完成，但不得让 Win32/Overlay 继续认为实体键处于按下。
- [ ] 参数窗口关闭、Toolbar 隐藏、Alt+Tab、Win 键、外部夺取 capture、缩放停止和 Renderer 销毁统一调用幂等 cancel。
- [ ] cancel 不触发按钮 click；迟到的真实 Up 不产生第二次 release、负计数或重复 action。
- [ ] UI layer/Presenter 重建时保留尚未确认的输入 generation，或执行一次明确 cancel；不得只清 DrawData 而遗留 ActiveID。

## F. 诊断与可证伪指标

### F1. 五段时间线

- [ ] Debug/开发者诊断为每个关键输入记录：`OS message dequeued`。
- [ ] 记录：`PendingInputBuffer snapshot/merge`。
- [ ] 记录：`ImGui::NewFrame consumed`。
- [ ] 记录：`Overlay DrawData/GPU draw completed`。
- [ ] 记录：`EndFrame/Present returned`，并关联 presenter、capture frameId、DLSSFG slot/generated 标记或 XeSSFG input frameId。
- [ ] 单独统计 queue wait、pacing wait、BeginFrame wait、keyed-mutex wait、UI build、GPU draw 和 EndFrame；不能只记录总延迟。

### F2. 必须满足的延迟指标

- [ ] 普通静态源下，P0 输入到 UI Present 提交不超过一个正常显示周期加调度余量；不能等待下一张捕获帧。
- [ ] 活动拖动时 UI 按显示刷新节奏更新，1000 Hz 鼠标不得导致无界 Present 或消息队列增长。
- [ ] DLSSFG 低输入帧率/暂停时，UI Present 延迟不随下一张 FIFO 帧等待时间增长，且 generated/real 顺序保持不变。
- [ ] XeSSFG 低输入帧率/暂停时，独立 UI layer 仍可更新，SDK 观察到的游戏颜色输入帧率不因 UI 操作增加。
- [ ] 任意模式下 button-up/cancel 到应用层 ownership=false 不超过一个消息调度周期；视觉释放不超过下一次可用 UI layer Present。

## 建议实施顺序

1. 增加五段输入到 Present 诊断，先量化普通/DLSSFG/XeSSFG 的真实阻塞点。
2. 建立 `PendingInputBuffer`、事件 sequence、合并规则和 presented acknowledgement，不改变 Presenter。
3. 把 DLSSFG 完整 Present 移出 WndProc，建立 P0～P3 Scheduler 和可中断等待。
4. 普通 Presenter 使用稳定最后底图完成静态源 UI-only Present。
5. DLSSFG 使用稳定前端底图完成不占 FIFO/ring 的 UI 合成。
6. XeSSFG 建立独立 DirectComposition UI layer，验证 SDK 输入率不变。
7. 完成输入生命周期、低帧率和异常路径矩阵后构建并覆盖部署。

## 完成定义

- 鼠标消息进入应用层缓冲后具有真实调度优先级，不再只是设置一个随后可能被 Presenter 拒绝的 dirty 标记。
- 连续 move 被有界合并；Down、Up、Wheel 和 Cancel 始终保序、无损且使用事件发生时坐标。
- 输入在所有长等待结束后、紧邻 `ImGui::NewFrame` 时注入；生成的 DrawData 与同一次成功 Present 对应。
- 捕获内容暂停或帧率很低时，工具栏、参数浮窗和软件光标仍按 UI/显示刷新节奏响应。
- 普通、DLSSFG、XeSSFG 的 UI 视觉响应一致，同时不破坏 DLSSFG FIFO 和 XeSSFG 输入帧合同。
- 不再需要 fixed settle、物理键轮询、额外兼容定时器或多套互相校正的输入状态。
