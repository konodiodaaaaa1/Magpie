## 1. 目标

- 将 DLSS SR、DLSS Frame Generation、DLSSNR 当前的 `Use Motion Vectors` 开关改为运动向量估计质量下拉菜单。
- 为 NVOF 固定四档可预测、可记录的网格/预设组合，不再自动选择第一个可用网格。
- 为两种 XeSS Frame Generation 效果增加光流方法下拉菜单，再根据所选方法显示对应的质量下拉菜单。
- XeSSFG 可在 NVIDIA、AMD、Intel 用户环境中继续使用；光流方法按运行时 capability 决定，不把 XeSSFG 与某个 GPU 厂商硬绑定。
- 不支持所选光流方法或质量档时，给出可行动的错误：改用其他方法、降低质量档或选择“无”。
- 多个效果同时消费运动向量时，共享相同提供器与最高请求质量，避免同一种光流重复执行。
- 保持第一帧、场景切换、resize、捕获中断、设备重建和运行时失败后的历史 reset 语义正确。

## 2. 明确不做

- 不把 2×2 SLOW、1×1 FAST/MEDIUM/SLOW 暴露为 r4 用户档位。
- 不根据瞬时 GPU 占用自动升降档，不实现“自动”质量。
- 不静默把 NVOF 切换成 AMDOF，也不静默把 2×2 降级为 4×4。
- 不将 AMD OF 的两档伪装成四档；AMD OF 仍严格采用独立 TODO 中的 50%/100% 输入分辨率方案。
- 不修改 FidelityFX Optical Flow 的固定 8×8 块、七层流程、shader、搜索范围、过滤或迭代次数。
- 不把 NVOFA 的官方 KITTI 错误率解释为最终 DLSS/XeSS 画质分数。
- 不在 r4 同时恢复学习型深度估算；Depth 合同继续保持当前 Zero/Flat 方案。
- 不允许光流档位在运行中无历史重置地热切换；所有方法/质量变化均为“应用并重新缩放”。

## 3. 用户可见合同

### 3.1 DLSS SR、DLSSFG、DLSSNR

以下三个效果使用相同的下拉菜单：

- `DLSS\DLSS_SR`
- `DLSSFG\DLSS_FrameGeneration`
- `DLSSNR\DLSSNR_AI_Filter`

用户可见标签建议为 `Motion Vector Estimation` / `运动向量估计`，选项为：

| 存储值 | 中文 | 英文 | NVOF 配置 | 默认 |
|---:|---|---|---|---|
| 0 | 无 | None | 不请求 NVOF；该消费者使用 Zero Motion |  |
| 1 | 性能 | Performance | 4×4 + FAST |  |
| 2 | 均衡 | Balanced | 4×4 + MEDIUM | 是 |
| 3 | 质量 | Quality | 4×4 + SLOW |  |
| 4 | 高质量 | High Quality | 2×2 + MEDIUM |  |

默认使用 `均衡`，因为当前实现等价于 4×4 + MEDIUM。这样旧配置迁移后不会无意增加性能开销。

用户第一处描述把第四档称为“超高质量”，随后给出的最终下拉列表为“高质量”。本文以后一处列表为 UI 真值：**用户界面显示“高质量”，内部枚举名为 `HighQuality`，对应 2×2 + MEDIUM**。如果发布前决定使用“超高质量”，只改显示文本，不改存储值和算法映射。

### 3.2 XeSS Frame Generation

同时覆盖：

- `XeSSFG\XeSS_FrameGeneration_x2_ZeroMV`
- `XeSSFG\XeSS_MultiFrameGeneration_ZeroMV`

第一项下拉菜单：`Optical Flow Method` / `光流方法`。

| 存储值 | 中文 | 英文 | 行为 |
|---:|---|---|---|
| 0 | 无 | None | 保持当前 Zero-MV 路径，不执行光流 |
| 1 | AMDOF | AMD OF | 使用 FidelityFX Optical Flow 提供器 |
| 2 | NVOF | NVIDIA OF | 使用 NVIDIA Optical Flow 提供器 |

默认值为 `无`，以保持已有 XeSSFG 配置与性能行为。

第二项下拉菜单始终对用户显示为 `Optical Flow Quality` / `光流质量`，但实际选项随方法变化：

| 光流方法 | 可见选项 | 默认 | 实际合同 |
|---|---|---|---|
| 无 | 隐藏或禁用 | 不适用 | Zero Motion |
| AMDOF | 性能、质量 | 质量 | 性能=50% OF 输入；质量=100% OF 输入 |
| NVOF | 性能、均衡、质量、高质量 | 均衡 | 4F、4M、4S、2M |

AMDOF 的“性能/质量”只代表 Magpie 的输入分辨率策略，不是 AMD 官方提供的两个算法预设。

### 3.3 XeSSFG 设置的持久化

不要把 AMDOF 两档和 NVOF 四档压进一个含糊的公共数值。建议持久化三个稳定参数：

```text
opticalFlowMethod          = None | Amd | Nvidia
amdOpticalFlowMode         = Performance | Quality
nvidiaOpticalFlowQuality   = Performance | Balanced | Quality | HighQuality
```

界面根据 `opticalFlowMethod` 只呈现一个名为“光流质量”的对应控件。这样用户在 AMDOF 与 NVOF 间切换时，可分别保留上次使用的质量，不需要把 NVOF 的 Balanced/HighQuality 错误映射到 AMDOF。

## 4. NVOF 四档选择依据

NVIDIA Optical Flow SDK 5.0 的 Ada 1080p 指示性数据如下；毫秒由本文按 `1000 / FPS` 换算，纵向指标是错误率，越低越好：

| 用户档位 | 网格/预设 | 约耗时 | NOC Fl-fg | NOC Fl-all | OCC Fl-fg | OCC Fl-all |
|---|---|---:|---:|---:|---:|---:|
| 性能 | 4×4 FAST | 0.77 ms | 29.90 | 23.48 | 32.44 | 33.07 |
| 均衡 | 4×4 MEDIUM | 1.00 ms | 23.66 | 19.11 | 26.36 | 28.98 |
| 质量 | 4×4 SLOW | 1.87 ms | 23.56 | 17.26 | 26.31 | 27.73 |
| 高质量 | 2×2 MEDIUM | 2.98 ms | 21.38 | 16.13 | 24.08 | 26.01 |

选择 2×2 MEDIUM 作为第四档的原因：它相对 4×4 SLOW 继续降低四项错误率，耗时增长仍明显小于 2×2 SLOW 与 1×1 模式。该映射是 Magpie 的产品档位，不应写成 NVIDIA 官方命名。

参考资料：

- [NVOFA Application Note 中文解读](../../NVOFA_Application_Note_中文解读.md)
- [NVIDIA NVOFA Application Note](https://docs.nvidia.com/video-technologies/optical-flow-sdk/nvofa-application-note/index.html)

## 5. 硬件与运行时能力合同

### 5.1 NVOF

- Turing（TU117 除外）只能使用 4×4，因此可使用性能、均衡和质量，不能使用高质量。
- Ampere、Ada 以及后续架构不按型号表硬编码；运行时查询 4×4/2×2 capability 后决定所选档位是否可用。
- 非 NVIDIA 适配器不得尝试加载并创建 NVOF session。
- `nvofapi64.dll`、API 版本、D3D11 接口、输入/输出格式和目标网格 capability 均必须通过。
- 4×4 档位不得因为硬件不支持 output cost 而一律失败。Turing 没有硬件 cost，提供器应允许 `enableOutputCost=false`，并由双向一致性或保守默认值构造 confidence。
- 高质量明确要求 2×2；若 capability 没有 2×2，返回“档位不支持”，不得偷偷使用 4×4 SLOW。

### 5.2 AMDOF

- `AMDOF` 指 FidelityFX Optical Flow 算法实现，不代表只能在 AMD 显卡运行。
- 不以 `VendorId == AMD` 作为唯一开关；NVIDIA、AMD、Intel 适配器只要满足实际 D3D/shader capability，均可尝试使用。
- capability 检测至少覆盖实现所需的 shader model、wave/intrinsic、格式、资源绑定和 `msad4` 路径。
- AMDOF 未编译、资源创建失败或必要 capability 不足时，返回明确的 AMDOF 不可用错误。
- 两档尺寸、向量尺度恢复、稠密化和计时完全引用 AMD OF 两档 TODO，不在 r4 另造第三档。

### 5.3 XeSSFG 与光流能力分离

XeSSFG SDK 是否能创建、多帧生成最大倍率是多少，与 NVOF/AMDOF 是否可用是两组独立 capability：

```text
XeSSFG 可用 && 光流方法=None      -> Zero-MV XeSSFG
XeSSFG 可用 && AMDOF 可用         -> AMDOF XeSSFG
XeSSFG 可用 && NVOF 档位可用      -> NVOF XeSSFG
XeSSFG 不可用                     -> 无论光流方法为何，XeSSFG 初始化失败
```

不得因为用户是 NVIDIA 或 AMD 显卡就提前断言 XeSSFG 不可用；以 Intel SDK 返回的实际支持结果为准。

## 6. 多消费者与多提供器解析

当前 `FrameGuidanceRequirements` 只有 `bool motion`，`FrameGuidanceService` 也只有一个 `_motionProvider`。r4 需要把“是否要 motion”提升为带方法和质量的请求。

建议内部模型：

```cpp
enum class OpticalFlowMethod : uint8_t {
    None,
    Amd,
    Nvidia
};

enum class NvidiaOpticalFlowQuality : uint8_t {
    Performance,
    Balanced,
    Quality,
    HighQuality
};

enum class AmdOpticalFlowMode : uint8_t {
    Performance,
    Quality
};

struct MotionVectorRequest {
    OpticalFlowMethod method = OpticalFlowMethod::None;
    uint8_t quality = 0;
};
```

解析规则：

1. `None` 不参与真实提供器创建，该消费者最终取得 Zero Motion。
2. 多个消费者请求 NVOF 时，只创建一个 NVOF context，使用请求中的最高档位；所有 NVOF 消费者共享该结果。
3. 多个消费者请求 AMDOF 时，只创建一个 AMDOF context；任一消费者请求质量档，就以 100% 质量档运行并共享。
4. 同一效果链同时请求 NVOF 与 AMDOF 时，允许各创建一个提供器，每个真实捕获帧各运行一次；不得让其中一个方法覆盖另一个。
5. 低档消费者可以消费同方法产生的更高质量结果，不另行降采样，也不重复执行低档提供器。
6. 日志同时打印每个消费者的请求值，以及该方法最终解析出的 session 级档位。

示例：

| 效果链请求 | 实际创建与执行 |
|---|---|
| DLSS SR=无，DLSSNR=均衡 | 一个 NVOF 4M；仅 DLSSNR 消费真实 Motion |
| DLSS SR=性能，DLSSFG=质量 | 一个 NVOF 4S；两者共享 |
| DLSSNR=高质量，XeSSFG=NVOF/均衡 | 一个 NVOF 2M；两者共享 |
| DLSSNR=均衡，XeSSFG=AMDOF/质量 | NVOF 4M 与 AMDOF 100% 各执行一次 |
| 所有消费者=无 | 不创建、不执行任何光流提供器 |

当前 `NvidiaOpticalFlowProvider` 按 `{4, 2, 1}` 选择第一个受支持网格，并固定 `NV_OF_PERF_LEVEL_MEDIUM`，因此所有现代 GPU 实际也优先使用 4M。

- [ ] 初始化阶段对“方法不可用”和“所选档位不可用”返回不同错误原因。
- [ ] resize 继续使用同一 profile 重建，不重新解释为其他档。

- [ ] None 时仍提供格式、尺寸和同步正确的 Zero Motion/Confidence，不给 NGX 传空指针。
- [ ] 非 None 时三者向 Frame Guidance 声明 NVOF 及指定档位。
- [ ] 每个消费者 Draw 时按自己的 request 取得 view；另一个效果启用 NVOF 不应强迫 None 消费者使用真实 Motion。
- [ ] 多个 DLSS 消费者的最高质量解析在日志中明确，例如 `requested=[SR:4M, NR:4S] resolved=4S`。
- [ ] `motionVectorQuality` 属于 `FrameGuidance` restart reason，不作为 Live 参数。
- [ ] 改档后完整重建提供器和受影响 NGX 历史，不能只改下帧的 perfLevel。
- [ ] 保持 motion direction、pixel unit、subrect、MVecScale 与当前已验证合同；档位只改变估计精度，不改变坐标语义。

验收：SR、FG、NR 单独与任意合法组合均能选择五项；None 不执行仅为该消费者服务的 NVOF；共享时只执行一次最高请求档。

## 13. P6：XeSSFG 真实运动向量数据路径

现状：`XeSSFGPresenter` 在 D3D12 中创建 `R16G16_FLOAT` 的 `zeroMotion12`，每帧固定将它标记为 `XEFG_SWAPCHAIN_RES_MOTION_VECTOR`；它不消费 Renderer 后台线程的 `FrameGuidanceService`。

- [ ] 在 Renderer 初始化最早阶段解析 XeSSFG 的 Method/Quality，并把请求加入全局 Frame Guidance 计划，而不只把 multiplier 传给 Presenter。
- [ ] 为 XeSSFG 建立“真实基础帧 + 相同 capturedFrameId 的 motion + reset”发布合同。
- [ ] 后台输出给前台的帧槽必须携带 capturedFrameId；不得只靠“最新 motion”猜测对应关系。
- [ ] 将适配到 XeSSFG 输入尺寸的 D3D11 motion 通过 NT shared handle 和 fence 暴露给 D3D12 Presenter；优先复用或抽取 `FrameGuidanceD3D12Interop` 的通用逻辑。
- [ ] 不做 CPU readback，不在前台输入/UI 线程执行无界等待。
- [ ] XeSSFG Presenter 只在 motion 的 frameId、extent、format、validRegion、sync 全部匹配当前真实基础帧时提交真实 motion。
- [ ] 任一项不匹配时，本帧提交 zeroMotion，并设置 `resetHistory=1`；不得提交上一帧 motion。
- [ ] NVOF/AMDOF 的 confidence 当前不直接传给 XeSSFG；若需要门控，应在共享 motion 纹理生成前完成，不臆造 XeSSFG 未公开的 confidence 输入。
- [ ] `constants.motionVectorScaleX/Y` 根据最终确定的 XeSSFG SDK 坐标合同填写；用固定平移素材验证后再锁定，不能因为当前 Zero-MV 使用 1.0 就默认真实 MV 也必然为 1.0。
- [ ] Method=None 继续使用本地 `zeroMotion12`，不创建跨设备 motion interop。
- [ ] 保持 flat depth、独立 UI layer、XeLL markers、proxy swap-chain 和 x2/x4 multiplier 逻辑不变。

验收：XeSSFG 每个真实基础帧使用完全匹配的运动向量；重复/生成/UI-only 帧不推进 OF；快速运动时不存在明显的一帧错位方向反转。

## 14. P7：方法与质量的条件 UI

- [ ] 设置页和 Overlay 对 XeSSFG 使用相同条件：None 隐藏两种质量；Amd 只显示 AMD 两档；Nvidia 只显示 NVOF 四档。
- [ ] 条件显隐不能只实现于设置页；缩放中 Overlay 必须一致。
- [ ] 隐藏参数继续持久化，但不进入当前 runtime request。
- [ ] 从 NVOF 切换到 AMDOF 后保留 NVOF 上次档位；切回时恢复。AMDOF 同理。
- [ ] DLSS 三效果没有方法下拉，避免给用户造成 AMDOF 可传入未验证 NGX 路径的暗示。
- [ ] 选中 None 后，质量控件消失且说明文字明确“使用零运动向量，不执行光流估计”。
- [ ] 设置页面可根据已选图形适配器做预检查并禁用明显不可能的 NVOF，但运行时 capability 查询仍是最终真值。
- [ ] 导入配置、GPU 改变或驱动改变后，不删除用户选择；启动时按实际 capability 给出错误。

验收：不同方法下不会出现无效质量项；设置页与 Overlay 的可见项、保存值和重启后实际行为一致。

## 15. P8：不支持与失败时的错误策略

### 15.1 启动前/初始化失败

所选方法或档位无法创建时，缩放启动失败并给出明确、可行动的错误；不静默切换方法或档位。

建议增加错误分类：

```text
OpticalFlowProviderUnavailable
NvidiaOpticalFlowUnsupported
NvidiaOpticalFlowQualityUnsupported
AmdOpticalFlowUnsupported
OpticalFlowInteropFailed
```

消息示例：

- `所选 NVIDIA OF“高质量”需要 2×2 输出网格，当前 GPU/驱动只报告 4×4。请选择“质量”或更低档位，改用 AMDOF，或选择“无”。`
- `当前适配器无法初始化 NVIDIA OF。请选择 AMDOF 或“无”。`
- `当前适配器不满足 AMDOF 所需能力。请选择 NVOF（若可用）或“无”。`

### 15.2 运行中失败

- [ ] 单帧失败不得继续提交旧 motion；当帧用 Zero Motion 并 reset 对应消费者历史。
- [ ] 连续失败达到有限阈值后，停止该方法在本次缩放会话中的执行，受影响消费者保持 Zero Motion。
- [ ] 通过非阻塞 UI 通知与日志说明“光流已停止”，但不因为光流辅助失败直接关闭整个缩放窗口。
- [ ] 运行时不自动启用另一个光流方法；用户可修改设置并应用/重新缩放。
- [ ] 方法停用后，不继续支付该方法的 dispatch 成本。

## 20. 完成定义

- 五个目标 Effect 都使用真正的下拉菜单，不再用裸整数滑块或独立 Motion 开关代替。
- NVOF 四档与 4F/4M/4S/2M 一一对应，运行日志可证明实际创建值。
- XeSSFG 能明确选择 None、AMDOF 或 NVOF，并只显示该方法合法的质量项。
- 不支持的方法/档位不会静默降级，错误明确告诉用户可选的下一步。
- 同方法多消费者只执行一次最高请求档；NVOF 与 AMDOF 可按需同时存在且不串线。
- XeSSFG 提交的真实 motion 与基础帧 frameId、尺寸、方向和同步点一致；不匹配时安全归零并 reset。
- 旧 DLSS 配置保持 4M，旧 XeSSFG 配置保持 Zero-MV。
- 所有方法/档位切换均通过“应用并重新缩放”生效，历史与资源生命周期无闪回、越界、设备移除或死锁。
