# v0.6.5 r3 fix4 TODO：修复 Overlay 左键释放饥饿与输入状态失配

基线：当前 `0.6.5` 分支上的 v0.6.5 r3 fix3 工作树，HEAD 仍为 `84d9f6abb8203a79f9a44d9a66984a293e68856d`。

本文只分析问题并列出后续实施内容；本轮不修改产品代码、不构建、不部署。

## 用户反馈

参数浮窗只要发生一次左键交互，松开实体鼠标后就可能继续保持拖动状态。窗口移动、参数滑条、滚动条、右下角 resize grip，以及浮窗自身的点击都受影响。该问题会使整个参数调节功能不可用，因此 fix4 的优先级高于继续增加 UI 或参数功能。

## 结论

### 1. 左键按下和释放已经分开，但没有在调度层获得不同优先级

- `ImGuiImpl::MessageHandler` 已分别处理 `WM_LBUTTONDOWN` 和 `WM_LBUTTONUP`，也分别调用 `AddMouseButtonEvent(0, true/false)`；因此不是简单缺少“按下/释放两个 case”。
- 真正缺失的是输入事务和消息优先级：鼠标移动可以合并，按下、释放和取消必须保序且不可合并，其中释放/取消必须抢在任何绘制和 present 前完成。
- 当前 `Renderer` 只通过一个 `_overlayInputNeedsSettle` 布尔值记录“之后需要多推进一轮”，不能表达明确的 `Pressed -> Released/Cancelled` 状态，也不能让尚未从 Win32 队列取出的 `WM_LBUTTONUP` 获得优先权。

### 2. 最可能的主因是前端帧消息饿死鼠标释放消息

- `ScalingRuntime::_ScalingThreadProc` 使用无过滤的 `PeekMessage(..., 0, 0, PM_REMOVE)`，并在内层 `while` 中持续清空消息队列。
- Win32 的默认取消息顺序会先处理 sent/posted message，再处理 input message。`WM_FRONTEND_RENDER`、`WM_FRONTEND_RENDER_DLSSFG`、`WM_OVERLAY_INPUT_TICK` 和 `WM_OVERLAY_REDRAW` 都是 posted message，`WM_LBUTTONUP` 是 input message。
- 同步 DLSSFG 每个生成帧和真实帧都会投递 `WM_FRONTEND_RENDER_DLSSFG`。前端消费一个 ring slot 后，后端可以立即填充并再次投递；因此 posted-message 队列可能持续非空，使已经发生的 `WM_LBUTTONUP` 长期无法被取出。
- 当前仅在 `WM_OVERLAY_REDRAW` 分支中用 `PeekMessage` 检查待处理 button-up，保护范围不包括 `WM_FRONTEND_RENDER` 和 `WM_FRONTEND_RENDER_DLSSFG`。当队列主要由 DLSSFG 前端帧消息占据时，该补丁无法建立全局公平性。
- 现有运行日志显示测试会话使用 `FrameRate_Filter + DLSSFG`，前端连续执行 DLSSFG FIFO 呈现；这与“所有浮窗控件都在一次点击后失去释放”的统一症状吻合。此结论属于基于代码和运行路径的高置信度推断，仍需用 fix4 诊断日志确认实际 button-up 的入队和出队时间。

### 3. `SetCapture` 是症状放大器，不是应直接删除的根因

- `SetCapture` 的用途是让拖动越过浮窗边界后，button-up 仍回到开始交互的缩放窗口；该能力应保留。
- 但 capture 只能决定消息送给哪个 HWND，不能改变消息泵从 posted/input 队列取消息的优先级。若 `WM_LBUTTONUP` 被饿死，Win32 capture、CursorManager capture 和 ImGui ActiveID 就会同时表现为“粘住”。
- 当前释放顺序还存在次要风险：先调用 `CursorManager::IsCursorCapturedOnOverlay(false)`，再调用 `ReleaseCapture()`。前者更新状态时，`GetGUIThreadInfo` 仍可能看到缩放窗口持有 Win32 capture，并短暂把它识别为前台窗口捕获。fix4 应先原子地结束 Overlay 所有权并安全释放 Win32 capture，再让 CursorManager 重算状态。
- 不应为了绕过症状永久移除 `SetCapture`，否则拖出浮窗释放会重新变成丢失 button-up；可以保留一个仅用于定位的开发者 A/B 开关，但最终产品路径应只有一套 capture 生命周期。

### 4. 两帧“settle”是脆弱补丁，不应承担正确性

- `OverlayDrawer::ProcessInput(settleButtonEdges)` 在释放时额外执行两轮 CPU-only ImGui frame，目的是让输入队列和 ActiveID 收尾。
- 这只有在 button-up 已经被窗口过程接收、事件已进入 ImGui 队列、input tick 又得到执行时才有效；它无法修复仍滞留在 Win32 input queue 中的释放消息。
- 正确性必须来自明确的边沿队列、按键所有权状态机和公平消息泵。额外 ImGui frame 只能作为版本行为兼容手段，并应在验证后删除或收敛，不能继续增加更多布尔标记和补帧次数。

## fix4 目标与边界

- 实体左键一旦松开，Overlay 的 CPU 按键所有权和 Win32 capture 必须立即结束，不受源帧率、DLSSFG 倍率、GPU present 或静态画面影响。
- `DOWN`、`UP`、`CANCEL` 是不可合并的有序边沿；`MOVE` 只保留最新位置，`WHEEL` 累积增量。
- 普通、DLSSFG、XeSSFG 共用同一输入状态机和消息公平规则；只允许最终视觉呈现策略不同。
- 保留参数窗口移动、resize grip、滚动条、Checkbox、Slider、Live apply、RestartRequired、窗口尺寸持久化和拖出窗口释放。
- 不改变效果器参数、步进、效果计算、帧生成 FIFO 顺序或 XeSSFG 输入帧合同。

## A. 先建立可证伪的输入诊断

### A1. 记录三个不同层级的状态

- [ ] 在 Debug/开发者日志中为每个鼠标按键边沿分配单调递增 sequence，记录 `WM_*BUTTONDOWN/UP` 到达窗口过程的时间、目标 HWND、`wParam`、实体键状态和 `GetCapture()`。
- [ ] 分别记录 Win32 消息已收到、ImGui 事件已入队、ImGui frame 已消费三个时间点；不能再只记录笼统的 input tick 次数。
- [ ] 每次边沿后记录 Overlay 所有权位、`_mouseButtonsDown`、CursorManager overlay capture、Win32 capture、`io.MouseDown[0]` 和 ImGui ActiveID；日志应能直接指出哪一层仍为 pressed。
- [ ] 记录消息泵在处理 button-up 前连续分发了多少条 `WM_FRONTEND_RENDER`、`WM_FRONTEND_RENDER_DLSSFG`、`WM_OVERLAY_*`，以及最老待处理输入的年龄。
- [ ] Release 构建不输出逐事件日志；统计只在 Debug/开发者模式启用，避免影响正常呈现时序。

### A2. 用物理状态确认“消息饿死”而非“鼠标未松开”

- [ ] 捕获期间定期读取 `GetAsyncKeyState(VK_LBUTTON/VK_RBUTTON)` 的高位，仅用于一致性检查和丢失释放的防御性恢复。
- [ ] 若物理键已抬起但 Overlay 所有权仍为 down，记录 stale duration、消息队列状态和当前 presenter，再合成一次幂等 cancel/release。
- [ ] 物理状态检查不得生成重复 click，不得把尚未被 ImGui 消费的快速 down/up 重排；它是安全网，不替代正常 `WM_*BUTTONUP`。

## B. 修复缩放线程的消息公平性

### B1. 给按键边沿最高优先级

- [ ] 重构 `ScalingRuntime::_ScalingThreadProc`：每次准备分发 posted render message 前，优先从队列取出并分发待处理的客户区与非客户区 button down/up、capture/cancel 输入。
- [ ] 至少覆盖 `WM_LBUTTONDOWN/UP`、`WM_RBUTTONDOWN/UP`、`WM_MBUTTONDOWN/UP`、`WM_XBUTTONDOWN/UP` 和对应非客户区消息；不能使用一个过宽数值区间误把不相关消息当作 release。
- [ ] 按下和释放保持原始先后顺序；如果同一次 pump 中同时存在 down/up，必须都进入 ImGui 队列，不能只保留最终布尔状态。
- [ ] 每处理有限数量的前端帧消息后必须返回检查 input queue；禁止 `while (posted queue 非空)` 无界地连续执行 present。
- [ ] 窗口关闭、设备错误、`WM_CANCELMODE` 和 capture loss 与 button-up 享有同等级别的控制消息优先权。

### B2. 保持 DLSSFG FIFO 顺序但不垄断窗口线程

- [ ] `WM_FRONTEND_RENDER_DLSSFG` 仍按 ring slot 的生成帧/真实帧顺序消费，禁止合并、跳过或重排 DLSSFG 帧。
- [ ] 公平调度只能在两次 DLSSFG frame dispatch 之间插入输入/控制消息，不能在单个 presenter `BeginFrame/EndFrame` 内重入绘制。
- [ ] 后端 ring 继续提供有界背压；输入优先只会短暂延后下一帧呈现，不允许通过扩大 ring 或无界投递来掩盖问题。
- [ ] 普通 `WM_FRONTEND_RENDER` 可以继续合并，但其合并循环也必须服从 input/control 优先级。
- [ ] XeSSFG 继续禁止用 Overlay-only 重复颜色帧充当 SDK 新输入；CPU 输入状态收尾与是否能够立刻显示分离。

### B3. 删除局部的 redraw 定时器绕行

- [ ] 全局消息公平性生效后，删除 `OVERLAY_REDRAW_TIMER_ID` 及 `WM_OVERLAY_REDRAW` 中只检查 button-up 的 `PeekMessage + SetTimer` 补丁。
- [ ] `WM_OVERLAY_REDRAW` 只负责视觉提交；它不再承担从输入队列“营救”释放消息的职责。
- [ ] 保持同一时刻最多一个 overlay input tick 和一个 overlay redraw pending；但 pending 标记不能吞掉按键边沿。

## C. 建立单一鼠标按键状态机

### C1. 明确状态与所有权

- [ ] 为每个按键使用明确状态：`Idle -> Pressed -> Released`，异常路径为 `Pressed -> Cancelled`；释放或取消完成后立即回到 `Idle`。
- [ ] 只有成功接收 Overlay 客户区 down 的按键才归 Overlay 所有；未归 Overlay 的 up 不得误操作 capture 或吞掉源窗口输入。
- [ ] 将“按键所有权”“Win32 capture”“CursorManager overlay capture”“ImGui queued state”分开记录，但只允许一个函数执行 acquire，另一个幂等函数执行 release/cancel。
- [ ] 删除正常 up 分支和 `_CancelMouseCapture` 中重复的释放代码，统一走同一结束事务，避免字段更新顺序分叉。

### C2. 规范 acquire/release 顺序

- [ ] Acquire：确认 Overlay 接收 down；若当前无其他 HWND capture，则对缩放窗口调用 `SetCapture`；记录所有权；设置 CursorManager overlay capture；最后向 ImGui 入队 down。
- [ ] 即使系统 capture 暂时不可取得，只要 Overlay 已接收 down，仍须保存按键所有权并入队；不能因为 `GetCapture()` 非空就让 down/up 落入不同处理路径。
- [ ] Release：先记录并入队 up，原子清除 Overlay 按键所有权和自有 capture 标记；若 Win32 capture 仍属于缩放窗口则调用 `ReleaseCapture`；最后清除 CursorManager overlay capture 并请求高优先级 input tick。
- [ ] 在调用 `ReleaseCapture` 前先清除内部 ownership，保证同步到达的 `WM_CAPTURECHANGED` 幂等，不重复添加 up/cancel。
- [ ] Cancel：对仍归 Overlay 的每个按键只合成一次 up，执行与正常 release 相同的 capture 清理，并标记为 cancelled 以阻止 click action。

### C3. 不再依赖 `WantCaptureMouse` 决定配对释放

- [ ] `io.WantCaptureMouse` 只用于决定一个新的 down 是否由 Overlay 接收；一旦 Overlay 拥有该按键，其 up/cancel 必须无条件送入同一状态机。
- [ ] Overlay 在按下后隐藏、关闭参数窗、自动隐藏工具栏或切换 presenter 时，配对释放仍能进入清理路径。
- [ ] 右键和双键交错使用相同规则；最后一个自有按键释放时才释放 Win32 capture。

## D. 精简 ImGui 输入推进

### D1. 边沿队列与移动快照分离

- [ ] 使用有界、有序的 button edge 队列保存 down/up/cancel；不得用 `_overlayInputNeedsSettle` 一个布尔值代表具体边沿。
- [ ] `WM_MOUSEMOVE` 只更新最新坐标和一个 dirty 标记；高轮询率移动不能产生无界消息或完整 ImGui frame 队列。
- [ ] Wheel 使用可累积的有界增量；不能因 move 合并而丢滚轮。
- [ ] 一个 input tick 按 sequence 消费所有尚未处理的边沿，再使用最新位置推进一次 UI 状态。

### D2. 移除“两帧即可释放”的正确性假设

- [ ] 首先验证 ImGui 1.91.8 在 `ConfigInputTrickleEventQueue` 默认行为下对同 tick down/up 的消费方式。
- [ ] 若 ImGui 必须跨 frame 消费快速 down/up，依据“队列仍有未消费边沿”明确安排下一 input tick，而不是传入 `settleButtonEdges=true` 后固定绘制两轮。
- [ ] ActiveID 清理完成后停止额外 CPU-only frame；不得因一次释放永久留下重绘循环。
- [ ] input tick 与 GPU present 继续解耦：ImGui 状态必须先释放，视觉结果可在下一次安全前端帧显示。

## E. 防御性释放路径

- [ ] `WM_CAPTURECHANGED`、`WM_CANCELMODE`、Alt+Tab/失焦、开始菜单、缩放停止、源窗口销毁、Renderer 销毁和设备丢失全部调用统一 cancel。
- [ ] 当 `GetCapture()` 已不属于缩放窗口时，不调用 `ReleaseCapture`，但仍清除 Overlay/ImGui/CursorManager 的逻辑状态。
- [ ] 当物理键已抬起且 up 消息超过一个输入调度周期仍未到达时，触发一次带日志的 failsafe cancel。
- [ ] 每次 input tick 结束执行 Debug invariant：物理键已抬起时不得同时存在 Overlay owned-down、CursorManager overlay capture 或持续的 ImGui MouseDown。
- [ ] 所有 release/cancel 路径幂等；重复 `WM_CAPTURECHANGED`、迟到的真实 button-up 或销毁清理不得产生第二次 click、负计数或崩溃。

## F. 回归与验收矩阵

### F1. 最小可用性门槛

- [ ] 单击浮窗空白区、标题、Checkbox、Slider、滚动条、底部按钮和右下角 resize grip，松开后立即恢复 Idle；后续点击无需重新开始缩放。
- [ ] 分别拖动浮窗、滑条、滚动条和 resize grip 30 秒，任意位置松开后立即停止，参数保持最后合法 step 值。
- [ ] 单击但不移动、快速 down/up、双击、拖出浮窗释放、左右键交错均不粘键。
- [ ] release 后 Debug invariant 在一个 input tick 内全部满足：Overlay owner=false、`GetCapture()!=scaling HWND`、CursorManager overlay capture=false、ImGui MouseDown=false、ActiveID 不再处于拖拽。

### F2. 呈现模式矩阵

- [ ] 普通呈现、DLSSFG x2/x3/x4、XeSSFG x2 和 XeSS Multi-Frame Generation 分别完成相同输入矩阵。
- [ ] 动态源、完全静态源、低帧率源、FrameRate Filter 限速源，以及 300 Hz 显示输出下均验证。
- [ ] DLSSFG 压力测试中记录 button-up 前连续处理的 frontend frame 数；修复后该数必须有明确小上限，不能随运行时间增长。
- [ ] DLSSFG generated-before-real 顺序、ring slot 释放和倍率无回归；XeSSFG SDK 看到的输入颜色帧率不因 Overlay 交互增加。

### F3. 生命周期和异常路径

- [ ] 拖动中 Alt+Tab、按 Win 键、打开开始菜单、让其他窗口夺取 capture、关闭参数窗、停止缩放和销毁源窗口，重新进入后可立即操作。
- [ ] 全屏/窗口模式、100%/125%/150%/200% DPI、多显示器跨屏拖动均不残留 capture。
- [ ] Release x64 构建、`git diff --check`、目标 GPU 手工矩阵全部通过后，才允许覆盖 `v0.6.5-r3-local`。

## G. 建议实施顺序

1. `diag(input): trace Win32 edge, queue wait, capture and ImGui consumption`
2. `fix(runtime): prioritize button/control input between frontend frames`
3. `refactor(input): introduce one ordered mouse-button state machine`
4. `fix(input): release Win32 capture before CursorManager recomputation`
5. `refactor(overlay): replace settle boolean with explicit pending edges`
6. `cleanup(window): remove overlay redraw timer workaround`
7. `test(input): stress normal, DLSSFG and XeSSFG capture lifecycle`
8. `build(release): rebuild and replace v0.6.5-r3-local`

## 完成定义

- 左键按下、释放和取消是三种明确、可追踪、不可被 move/redraw 合并的事件。
- posted frontend frame 再密集，也不能让 button-up/cancel 等待超过一个有界调度周期。
- Win32 capture、Overlay 所有权、CursorManager 和 ImGui ActiveID 始终由同一输入事务收敛，不再出现任一层长期保持 pressed。
- 参数窗口的移动、resize、滚动、Slider、Checkbox 和按钮均恢复可用；普通、DLSSFG、XeSSFG 共用同一正确输入生命周期。
- 保留帧生成顺序与实时参数能力，不再用增加 settle frame、timer 或分散布尔标记掩盖释放问题。
