# 0.6.5 r9：A–D 实施记录

2026-09-05。用户批准执行 [r9 调查报告](../reviews/20260905-v0.6.5-r9-dlssnr-switching-stutter-REVIEW.md) 的 A、B、C、D。

## 实现

| 项目 | 已实现的行为 | 边界 |
| --- | --- | --- |
| A | WGC 复制前检查 ContentSize、源纹理尺寸与裁剪框；拒绝时间戳未前进的帧；无效期间不调用效果推理，保留上一帧；恢复首帧绕过旧序列重复检测一次 | 不要求内容尺寸等于帧池尺寸；不改变正常连续帧的精确／动态重复检测策略 |
| B | 重启失败存为持久错误状态；清理半成品会话与帧池；分别捕获启动、取帧、关闭的 WinRT 异常；详情保留阶段与 HRESULT | 采用现有捕获错误退出通道，不进行无限重试 |
| C | 会话重启、无效内容／时间戳恢复及原始捕获时间戳间隔 ≥500 ms 建立新序列；恢复首帧重置共享光流历史和 DLSSFG 历史，清除旧队列等待，重建间隔基线 | 普通焦点消息仍保留原有历史请求，但不无差别重置节奏；使用原有后端到达间隔减队列等待估计，未把原始捕获时间戳直接替换为呈现间隔 |
| D | 三槽 FIFO；GetData 使用 DONOTFLUSH、S_FALSE 立即返回；采样槽满则跳过；校验 CreateQuery、GetData、频率、单调时间戳及 pass 数量；锁外读取、短锁发布 | 查询本身不触发额外 Flush；依赖正常发布提交；不修改已存在的跨设备 fence 同步 |

恢复状态仅由后端线程读写，前端通过既有消息、错误回调及共享图像消费结果。捕获恢复首帧先建立有效输出，再同步重置历史，随后 BeginFrame／效果 Draw；不能由旧画面重绘提前消耗恢复状态。

明确中断后，使用 250 ms 后端消息定时器维持检查，约 5 秒仍没有有效输入则报告捕获失败；初次启动无首帧同样有出口。等待期间每 250 ms 唤醒既有前端 SrcTracker 检查，尺寸／最小化变化走原有重建。正常健康状态下静止画面可以无限期没有新帧，不启动恢复超时。最低帧率到期时也不会进入空转重绘。

恢复首帧的呈现间隔使用最后健康估计；首个新帧对直接建立新基线，然后继续 0.2 权重平滑。尚无历史估计时以源帧 60 FPS 回退并遵守限帧，再除以补帧倍数。旧的 ≥500 ms 后端长停顿检测保留，同样避免把停顿样本混入持续帧率估计。

性能查询未完成超过约 5 秒时，在后续非阻塞轮询中停用本次采集；查询错误和非法频率／时间戳直接停用。Disjoint 是可丢弃的无效采样，不当作致命错误。停止或更改 pass 数量会退役旧槽，用户再次打开监视器可重新创建采集会话。

## 诊断字段

- `WGC capture interrupted`、`WGC session started`：序列、会话代次、原因。
- `WGC rejected frame`：每次异常序列首次记录内容尺寸、纹理尺寸、裁剪框和新旧时间戳。
- `WGC valid capture restored`：恢复耗时、拒绝帧总数、首帧尺寸和时间戳。
- `Capture sequence accepted`：恢复进入渲染的帧号与历史重置请求；该字段表示请求，不作为 SDK 内部恢复成功的证据。
- `Capture duplicate readback CPU wait`：每 120 次精确比较统计 Map／Unmap 的 CPU 等待均值与最大值，不等同于纯 GPU 算法耗时。
- `Backend publication CPU timing`：每 120 次发布统计共享纹理事务和 signal／flush／fence 等待均值与最大值，并记录性能采集状态。事务包括锁和 keyed mutex 等待、CPU 复制命令提交；fence 可能涵盖先前 GPU 工作，不能当作独立复制 GPU 时间。
- `Effects profiler`：开始／停止、首次槽位忙、跳过样本总数与关闭采集原因。正常查询不逐帧打印日志。

原有 DLSSFG 槽位等待、捕获／入队计数及呈现统计保留。没有直接修改 NR 模型、残差重建、默认光流质量或跨设备同步。

## 用户验收重点

1. NR 80%／100%，单独 NR 以及 NR + FG：Alt+Tab、多显示器操作再切回，观察能否恢复与异常帧情况。
2. 切回静止画面也应处理一次恢复首帧，后续恢复正常重复帧复用。
3. 恢复期间窗口尺寸或最小化状态发生变化，确认自动重建流程继续工作；健康静止窗口不应因五秒无新画面而停止。
4. 性能监视器关闭／打开／拖动，使用相同内容、限帧、光流配置对比日志；补充高分辨率场景。
