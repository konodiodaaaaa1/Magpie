# v0.6.5 r3 fix3 TODO：参数完整性与低延迟 Overlay 输入

基线：当前 `0.6.5` 分支上的 v0.6.5 r3 fix2 工作树，HEAD 仍为 `84d9f6abb8203a79f9a44d9a66984a293e68856d`。

对比目标：v0.6.5 r3 初次部署与当前 v0.6.5 r3 fix2。初次部署包已被同名 `v0.6.5-r3-local` 覆盖，无法再做可执行文件级哈希差分；本文依据 r3、r3 fix1、r3 fix2 的实施记录、当前源码和仍保留的效果文件进行行为与代码路径对比。本文只列出 TODO，不修改产品代码、不构建、不部署。

## 用户反馈

1. 与 r3 初次部署相比，当前参数浮窗中有很多原本可调节的参数不再显示或无法到达。
2. 拖动参数浮窗、调整浮窗尺寸和拖动浮窗内参数时，松开鼠标后仍会出现延迟释放。
3. 需要审查 r3 fix1/fix2 增加的功能，删除没有必要的复杂度，保留参数实时调节、可靠释放和窗口可调整大小的核心能力。

## 对比结论

### 1. 没有证据表明参数定义被成批删除

- r3 fix1/fix2 没有以“减少可调参数”为目标，也没有修改普通效果器的参数暴露合同。
- 当前 `effects` 目录仍有 193 个效果文件。与 r2 保留包相比，仅 DLSSFG 和 XeSS Multi-Frame Generation 两个 HLSL 文件内容不同，其 `//!PARAMETER`、范围和步进指令数量没有减少。
- 当前 Overlay 遍历每个活动 `EffectDesc::params`，没有按 `Live`/`RestartRequired` 隐藏参数；不能实时应用的参数也应显示并允许修改 draft。
- 当前唯一明确的参数跳过规则是 DLSSNR：关闭 `enableInputResolutionScaling` 时隐藏 `inputResolutionPercent` 和五个 residual 控制项，共 6 项。这与主窗口的依赖显隐规则一致。
- 因此“很多参数不显示”应先按 UI 可达性回归处理，而不是重新添加参数元数据。必须用声明数、条件隐藏数和实际绘制数证明最终结论，不能只靠肉眼判断。

### 2. 当前布局会让“仍存在的参数”看起来像消失

- r3 初次部署的参数窗口使用约 420 DIP 固定宽度和自动高度；fix1 改为默认约 `420 x 600 DIP` 的可调整窗口并保存用户尺寸。
- fix2 又永久预留四行状态区，以及最多两行按钮区。即使没有任何状态，四行高度也不会归还给参数内容区。
- 所有效果器和参数目前共用一个纵向滚动 child；长标签还会为每项追加 `[Live]` 或 `[Restart required]`，窄窗口下频繁换行，进一步减少同屏参数数目。
- 如果滚轮、滚动条或拖拽释放同时存在延迟，下方参数虽然仍被绘制，却会表现为无法到达或“不显示”。
- 已保存的小尺寸会跨会话恢复，使一次偶发的窄/矮布局持续存在；当前没有“一键恢复合适尺寸”或清晰的参数总数/隐藏数提示。

### 3. fix2 保证了消息归属，但没有解决输入调度延迟

- `SetCapture`/`ReleaseCapture` 解决的是鼠标移出窗口后 button-up 送达哪个 HWND，不应删除这一可靠性保障。
- 当前捕获期间的每个 `WM_MOUSEMOVE` 都会直接进入 `Renderer::MessageHandler`：更新 CursorManager，然后在普通路径执行 `Render(true)`，在 DLSSFG 路径尝试 Overlay-only present，在 XeSSFG 路径立即执行 ImGui input tick。
- `OverlayDrawer::_Draw` 每次至少推进两轮 ImGui frame；控件产生 `changed` 时还可能增加轮数，循环上限为 10。该工作直接发生在缩放窗口的消息处理链中。
- 高频鼠标移动没有实现 r3 fix2 TODO 已要求的 pending/coalescing。窗口消息线程忙于重复布局、绘制或 present 时，排在后面的 `WM_LBUTTONUP` 会较晚得到处理，于是窗口移动、resize grip 和滑条都会出现同一种“延迟释放”。
- 这不是三个控件各自的错误，而是统一输入路径的背压问题。不能分别给滑条、窗口移动和 resize 打补丁。

## 目标与边界

- 所有当前活动效果器的公开参数必须有可审计的去向：显示、带明确原因的条件隐藏，或明确声明为内部参数；禁止静默丢失。
- 鼠标消息处理只负责记录输入和维护捕获，不在高频 `WM_MOUSEMOVE` 中同步执行完整绘制或 present。
- button-up/cancel 的 CPU 状态释放优先于视觉刷新；即使 GPU、DLSSFG FIFO 或 XeSSFG presenter 忙碌，也必须立即结束捕获。
- 保留窗口移动、用户 resize、参数 step、Live/RestartRequired、保存、还原和应用并重新缩放。
- 精简重复状态和重复调度，不改变效果器计算、参数范围、默认值或 r2 已确定的参数分组语义。
- 不恢复已明确取消暴露的 `NR Preset`，不恢复已移除的深度估算功能。

## A. 参数完整性与可达性

### A1. 建立参数显示清单

- [ ] 在参数窗口构建阶段，为每个活动效果器统计 `declaredCount`、`drawnCount`、`conditionallyHiddenCount` 和 `invalidCount`。
- [ ] 每个 `EffectDesc::params` 项必须进入以下一种状态：`Visible`、`ConditionallyHidden`、`InvalidButVisibleDisabled`；普通错误不得通过 `continue` 静默消失。
- [ ] 仅保留有明确依赖合同的条件隐藏。当前 DLSSNR 合同为：输入分辨率调整关闭时隐藏 `inputResolutionPercent`、`residualMultiplier`、`residualSaturation`、`residualLightness`、`shadowStructureMultiplier`、`reflectionGlowMultiplier`。
- [ ] DLSSNR 共 15 个公开参数；输入分辨率调整关闭时应显示 9 项、条件隐藏 6 项，开启时应显示 15 项。`NR Preset` 不计入公开参数。
- [ ] 对参数描述非法、step 无法离散化或 runtime capability 缺失的情况，仍显示灰色控件和原因 tooltip，并记录日志；不能让用户误以为参数被删除。
- [ ] 仅在开发者模式或诊断日志中输出计数，正常用户界面不增加永久调试噪声。

### A2. 恢复所有参数的可达性

- [ ] 验证内容 child 始终拥有非负且可操作的高度；窗口过矮时优先限制最小高度，不能创建接近零高度的参数区。
- [ ] 为参数内容区保留清晰可见的纵向滚动条；鼠标滚轮、拖动滚动条和 Page Up/Page Down 均能访问最后一项参数。
- [ ] 打开参数窗口时，如果保存尺寸来自旧布局且不足以容纳当前固定区域，执行一次带版本号的尺寸迁移，而不是永久沿用过小尺寸。
- [ ] 增加“恢复默认窗口大小”入口，或在窗口尺寸/视口异常时自动恢复约 `420 x 600 DIP` 的安全值；不得影响用户正常保存的合理尺寸。
- [ ] 记录并验证首项、末项的可达性：无论效果链长度、DPI、语言和窗口尺寸如何，最后一个效果器的最后一个参数都能滚动到并操作。

### A3. 宽窗口的响应式分组

- [ ] 窄窗口继续按单列纵向显示，避免每列过窄。
- [ ] 用户把窗口拉宽且某个效果器包含多个 `//!GROUP` 时，允许按组形成响应式多列；组顺序、参数顺序和 24px/DIP 视觉间距与主窗口保持一致。
- [ ] 多列只用于提高可见性，不能引入水平滚动作为访问参数的必要条件；宽度不足时自动退回单列。
- [ ] 分隔线使用淡细竖线，不参与命中测试，不覆盖滑条、tooltip 或滚动条。
- [ ] 无组效果器保持单列；不要为只有一个组的普通效果增加空列或额外留白。

## B. 低延迟输入与可靠释放

### B1. 把输入消费与 GPU 呈现解耦

- [ ] `ImGuiImpl::MessageHandler` 只排入按键/滚轮事件、更新最新鼠标位置快照并维护 Overlay 捕获状态；禁止从单个 `WM_MOUSEMOVE` 同步触发完整 GPU present。
- [ ] 收到配对的 `WM_LBUTTONUP`/`WM_RBUTTONUP` 时，立即清除 Overlay 按键所有权和 CursorManager 捕获，并安全调用 `ReleaseCapture`；这些 CPU 清理不得等待 ImGui 绘制、后台参数应用或 presenter。
- [ ] button-up/cancel 后安排一次高优先级 UI tick，让 ImGui ActiveID 在下一次调度中收尾；即使该 tick 的画面稍后呈现，也不能继续把鼠标当作按下。
- [ ] 保留 `WM_CAPTURECHANGED`、`WM_CANCELMODE`、窗口销毁和缩放停止的统一取消路径；正常释放与异常取消保持幂等。

### B2. 合并高频鼠标移动

- [ ] 新增单一 `RequestOverlayInputTick`/`RequestOverlayRedraw` 调度入口，使用原子或窗口线程内 pending 标记保证同一时刻最多存在一个未处理任务。
- [ ] 多个 `WM_MOUSEMOVE` 只覆盖“最新位置”，不为每个硬件采样执行两轮以上 ImGui frame，也不无限堆积 dispatcher lambda 或自定义窗口消息。
- [ ] 每个实际 UI tick 消费最新位置和所有必须保序的 button/wheel 边沿；移动可以合并，按下、抬起和取消不能丢失或乱序。
- [ ] Live 参数继续通过现有 last-write-wins mailbox 合并；UI 调度合并和 backend 参数合并使用各自清晰的所有权，不建立第二条无界队列。
- [ ] 拖动时以显示刷新率或一个明确上限节流 Overlay 视觉刷新；释放事件不受该节流等待影响。

### B3. 统一普通、DLSSFG 与 XeSSFG 的输入阶段

- [ ] 三种呈现路径先共用同一个 CPU-side Overlay input tick，统一推进 ImGui 的输入、ActiveID、窗口位置/尺寸和参数 draft。
- [ ] input tick 完成后再按 presenter 能力选择视觉提交：普通路径使用安全前台帧，DLSSFG 使用私有基础帧且不消费 FIFO slot，XeSSFG 不把重复颜色帧提交为 SDK 新输入。
- [ ] 删除 `Renderer::MessageHandler` 中“每种 presenter 各自立即处理鼠标消息”的重复分支；分支只保留呈现策略，不再复制输入生命周期。
- [ ] DLSSFG FIFO 忙或 XeSSFG 暂时不能 present 时，只保留一个待刷新标记；下一次安全时机显示最新 UI，不回放过时的每个鼠标位置。
- [ ] 不在窗口过程内等待 DWM、GPU fence、pacing deadline 或后台效果更新；这些等待不能阻塞 button-up、关闭和设备错误消息。

### B4. 延迟诊断

- [ ] 在开发者日志中记录 `message received -> input tick -> Overlay present` 三个时间点，并区分普通、DLSSFG、XeSSFG。
- [ ] 记录单次消息处理耗时、合并的 move 数量、pending tick 数量和 capture 持续时间；正常路径 pending tick 必须为 0 或 1。
- [ ] button-up 到 CPU 捕获释放应在同一次窗口消息处理中完成，不以 GPU 帧时间作为验收条件。
- [ ] 为视觉响应设定可观察目标：动态源中下一显示帧更新，静态源中不超过一个调度/刷新周期；若 presenter 受限，日志必须能区分“输入已释放”和“画面尚未刷新”。

## C. 功能精简

### C1. 精简底部状态区

- [ ] 删除永久占用四行的四槽状态区，改为固定高度的一行摘要，最多两行；无状态时仍保留相同高度以避免参数区跳动。
- [ ] `Live applied` 不作为永久状态占用一行。参数成功实时应用可短暂显示，或只在失败时给出可见提示。
- [ ] 将“未保存”和“有 N 项等待重新缩放”合并为一个确定性摘要；保存/重启处理中和错误优先覆盖摘要，完整信息放入 tooltip。
- [ ] 状态区仍位于最底部，出现、消失或文本变化不得改变参数 child 的高度、顶部和 `ScrollY`。

### C2. 精简每项参数的重复标记

- [ ] 不再把完整 `[Live]` / `[Restart required]` 文本拼进每个长标签；改为紧凑图标、短徽标或右侧标记，并提供 tooltip。
- [ ] 在窗口顶部或底部提供一次简短图例，避免每项重复长文本导致换行和纵向膨胀。
- [ ] RestartRequired 参数必须继续可编辑，且其“保存后需重新缩放”的语义不可因视觉精简而弱化。

### C3. 保留与删除的能力

- [ ] 保留：参数窗口移动、右下角 resize grip、尺寸持久化、step 离散化、Live apply、restart draft、还原、保存、应用并重新缩放、Win32 capture。
- [ ] 删除或合并：每个 mouse-move 的同步完整 render、三套 presenter 输入分支、永久 `Live applied` 状态槽、重复的长状态文字。
- [ ] 不再通过增加更多布尔标记修复状态；以“按键所有权、系统 capture、input tick pending、redraw pending”四类最小状态建模，并写清各自线程所有权。
- [ ] 不把问题绕回“只在松开鼠标后提交参数”；Live 参数在合法离散 tick 改变时仍实时提交。

## D. 防御性检查

- [ ] 检查 `_startupEffectParameterValues`、`_draftEffectParameterValues`、runtime info 和 `ActiveEffectDescs` 的效果器/参数索引完全对齐；自动追加的 Bicubic 只能被明确排除，不能截断用户效果器。
- [ ] 效果链中某一项无参数、解析失败或被条件隐藏时，后续效果器仍继续显示，不能因计数或 child 布局提前结束。
- [ ] 调整窗口尺寸、跨显示器 DPI、关闭并重开参数窗、参数触发完整重启后，显示计数和滚动范围重新计算且没有陈旧状态。
- [ ] 窗口标题拖动、resize grip、滚动条、Slider、Checkbox 和底部按钮共用同一捕获规则；没有控件私自调用另一套 capture/release。
- [ ] 右键、左右键交错、拖出窗口释放、Alt+Tab、Win 键、源窗口销毁、设备丢失和缩放退出后均不残留 Win32 capture、CursorManager capture 或 ImGui ActiveID。

## 完成定义

- 参数定义没有被静默丢弃；每个活动效果器都能给出准确的声明、显示和条件隐藏计数，所有应显示参数均可到达并操作。
- `WM_MOUSEMOVE` 不再同步触发一次完整 render/present；高频移动被合并，按键边沿保持顺序且不丢失。
- 收到 button-up/cancel 时立即结束 CPU 捕获状态，视觉刷新或帧生成阻塞不会表现为继续拖动。
- 普通、DLSSFG 和 XeSSFG 共用一套输入生命周期，只在最终呈现方式上分流。
- 参数窗口默认视图比 fix2 更紧凑，状态提示仍固定在最下面且不引发布局跳动；窗口移动、调整大小、滚动和多列分组均无回归。
