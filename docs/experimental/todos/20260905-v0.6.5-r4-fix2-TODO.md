## 2. `OF Quality` 空白的直接根因

### 2.1 元数据、解析和值映射均存在

源目录和 `r4 local` 部署目录中的以下效果均含有完整 `//!OPTION`：

- `DLSSFG\DLSS_FrameGeneration`：`1 Performance / 2 Balanced / 3 Quality / 4 Ultra Quality`。
- `DLSSNR\DLSSNR_AI_Filter`：同上。
- `XeSSFG\XeSS_FrameGeneration_x2_ZeroMV`：Method 三项、AMDOF 两项、NVOF 四项。
- `XeSSFG\XeSS_MultiFrameGeneration_ZeroMV`：当前也含上述三组，fix2 将按第 6 节收口。

`EffectParametersViewModel` 已把 `EffectParameterDesc::choices` 转成 `(value, label)`，`ChoiceIndex` 也正确通过 `_choiceValues` 处理 `1..4` 这种非零起始值。Overlay 能显示并实时应用相同选项，进一步证明效果解析、缓存和参数持久化不是空白原因。

### 2.2 XAML 绑定已经执行，但集合不可被 ItemsControl 枚举

当前合同为：

```text
IDL:       IVector<String> Choices
C++:       IVector<hstring> _choices
构造:      single_threaded_vector(std::vector<hstring>)
XAML:      ItemsSource="{x:Bind Choices, Mode=OneWay}"
```

生成的 `ScalingModesPage.xaml.g.hpp` 明确执行：

```cpp
Update_Choices(obj.Choices(), phase);
obj.ItemsSource(value);
```

所以问题不在 `x:Bind` 漏生成或属性通知漏触发。问题发生在 `ItemsSource` 收到被擦除为 `IInspectable` 的对象后尝试枚举时。

本机 Windows SDK `10.0.26100.0` 的 C++/WinRT 实现显示：

- `single_threaded_vector<T>` 的实现只提供 `IVector<T>`、`IVectorView<T>`、`IIterable<T>`。
- `single_threaded_observable_vector<T>` 对非 `IInspectable` 类型使用 `convertible_observable_vector`，同时提供强类型接口和 `IObservableVector<IInspectable>`、`IVector<IInspectable>`、`IIterable<IInspectable>`。

XAML 的 `ItemsSource` 需要可在运行时枚举的 inspectable/bindable 集合。普通 `IVector<String>` 的泛型 IID 不能靠对象的 `IInspectable` 身份推断出来，因此控件获得非空对象却得到零个可显示项。这也解释了为什么前一次把自定义对象改回字符串后仍无效果：元素类型变简单了，但集合的运行时形状没有改变。

参考：

- [C++/WinRT 集合](https://learn.microsoft.com/windows/apps/develop/cpp-winrt/collections)
- [将集合绑定到 XAML 控件](https://learn.microsoft.com/windows/apps/develop/cpp-winrt/binding-collection)
- [C# 到 C++/WinRT：集合与运行时泛型接口](https://learn.microsoft.com/windows/apps/develop/cpp-winrt/move-to-winrt-from-csharp)

### 2.3 唯一允许的 UI 根因修复

- [ ] 将 `ScalingModeParameter.Choices` 的 IDL 合同从 `IVector<String>` 改为 `IObservableVector<String>`。

- [ ] `_RebuildChoices` 只使用 `single_threaded_observable_vector<hstring>` 创建集合；优先保留同一实例并 `ReplaceAll`，由 `VectorChanged` 更新控件。

## 4. XeSSFG 闪退的证据链

### 4.1 现场日志的边界

报告闪退的三次进程发生在：

```text
2026-09-05 03:05:39/40
2026-09-05 03:06:05/07
2026-09-05 03:06:20/21
```

当前 `r4 local/logs/magpie.log` 从 `03:15:44` 开始，晚于三次崩溃。它只保留后续启动和测试，因此不能用它声称 XeSS SDK 返回了某个错误。后续调查必须区分：

1. 导致 Renderer 提前返回的首个错误；
2. 清理阶段把首个错误升级为进程崩溃的第二个错误。

### 4.2 崩溃转储直接证明第二个错误

三次事件日志均指向相同 fault offset：

```text
Exception: 0xC0000005 (随后由 WER 记录 0xC000041D)
Fault RVA: 0x001B4806
Instruction: mov rbx, qword ptr [r14+0E0h]
r14: 0x0
Read address: 0xE0
```

六份对应 dump 位于 `%LOCALAPPDATA%\CrashDumps`。旧可执行文件的匹配 PDB 已被覆盖，但该故障指令周围字节序列在当前同源构建中唯一映射到：

```text
ScalingWindow::WM_DESTROY
  -> Renderer::ClearOverlayStates
  -> OverlayDrawer::ClearStates
  -> ImGuiImpl::ClearStates
  -> ImGui::GetIO()
```

`Renderer::Initialize` 在创建 Overlay 之前有多条合法失败返回；而 `WM_DESTROY` 只检查 `_renderer != nullptr`，不检查 Overlay/ImGui 是否初始化。`ImGuiImpl::ClearStates` 又在重置 Magpie 自有状态之前无条件取得 `ImGuiIO`。此时全局 `GImGui == nullptr`，因此在 ImGui 内部读取固定偏移时访问冲突。

这不是 XeSS SDK 内部崩溃，也不是光流纹理越界；它是 Magpie 的部分初始化清理不满足生命周期不变量。

### 4.3 本次首个失败的最强证据

调查开始时捕获到的现场缩放链曾同时包含：

```text
FrameRate_Filter
XeSSFG\XeSS_FrameGeneration_x2_ZeroMV
XeSSFG\XeSS_MultiFrameGeneration_ZeroMV
```

`Renderer::Initialize` 在 Overlay 初始化前统计 XeSSFG marker；数量大于 1 时立即记录：

```text
Only one XeSS Frame Generation effect is allowed
```

随后返回 `ScalingFailedGeneral`，完全符合上面的空 ImGui 清理路径。现场配置之后在 `03:34:06` 被保存为只含 x2，所以当前 `config.json` 不能再作为崩溃时快照；原 `magpie.log` 也已被后续启动覆盖。基于代码的确定性分支和调查时捕获的配置，本次首个失败高度确定为两个 XeSSFG marker 冲突，但 fix2 回归仍须用新日志分别验证“仅 x2”和“仅 MFG”，不能跳过 SDK 初始化测试。

## 6. P1：收口 XeSSFG MFG 的硬件和光流合同

### 6.1 正确区分 x2 与 MFG

随附 XeSS 3.0.1 开发指南 `dependencies/XeSS-SDK-3.0.1/doc/xess_fg_developer_guide_english.md` 的 Requirements 明确说明：非 Intel GPU 最多生成一帧。代码中 `requestedInterpolations = multiplier - 1`，因此：

| 模式 | multiplier | 生成帧数 | 目标硬件 |
|---|---:|---:|---|
| XeSSFG x2 | 2 | 1 | 支持 XeSS-FG 的 Intel / NVIDIA / AMD |
| XeSSFG MFG x3 | 3 | 2 | Intel Arc 系列且 SDK 报告能力满足 |
| XeSSFG MFG x4 | 4 | 3 | Intel Arc 系列且 SDK 报告能力满足 |

- [ ] x2 marker 固定为 `2x`。
- [ ] MFG 的 multiplier 范围从 `2..4` 收紧为 `3..4`，显示名同步为 `XeSS Multi-Frame Generation x3-x4`。
- [ ] Renderer 解析 marker 时保存明确的 `X2/MultiFrame` variant，不能只剩一个 multiplier 数字。
- [ ] MFG 首先要求实际选中适配器 VendorId 为 `0x8086`；这只是早期可行动错误，不替代 SDK capability。
- [ ] 创建 XeSSFG context 后以 `xefgSwapChainGetProperties().maxSupportedInterpolations` 为最终依据。
- [ ] `maxSupportedInterpolations < multiplier - 1` 时停止启动并报告“不支持所选 MFG 倍率”。
- [ ] 删除当前 `std::min(requested, maxSupported)` 的静默降档；用户选择 x4 不得在后台变成 x3 或 x2。
- [ ] Intel VendorId 但 context 创建失败或最大插帧数不足时同样报能力不支持，不维护易过时的 DeviceId 白名单。

### 6.2 MFG 仅接入 AMDOF

- [ ] 从 `XeSS_MultiFrameGeneration_ZeroMV.hlsl` 删除 `//!OPTION 2 NVOF`。
- [ ] 从 MFG marker 删除整个 `nvidiaOpticalFlowQuality` 参数。
- [ ] MFG `opticalFlowMethod` 只接受 `0=None`、`1=AMDOF`。
- [ ] AMDOF 质量只接受 `0=Performance`、`1=Quality`。
- [ ] AMDOF 不按 GPU VendorId 禁止；由 FidelityFX/设备 capability 初始化结果决定是否可用。
- [ ] Intel Arc 上 AMDOF 初始化失败时使用现有 `AmdOpticalFlowUnsupported` 或更准确的跨厂商文案，进程不得退出。
- [ ] Method=None 时不创建 AMDOF provider，给 XeSSFG 提交 Zero Motion，并按首帧/切换规则 reset history。

### 6.3 配置归一化

当前 `NormalizeV065ScalingModes` 对 x2 和 MFG 共用 `0..2` 的 Method 范围。fix2 必须分开：

- [ ] x2：保留 `opticalFlowMethod=0..2`、AMDOF `0..1`、NVOF `1..4`。
- [ ] MFG：`opticalFlowMethod=0..1`、AMDOF `0..1`，删除遗留 `nvidiaOpticalFlowQuality`。
- [ ] 旧 MFG 的 `opticalFlowMethod=2` 必须回退为 `None(0)` 并记录一次迁移；绝不能 clamp 成 `AMDOF(1)`。
- [ ] 旧 MFG multiplier `2` 回退为默认 `3` 并记录一次迁移；不得继续把 MFG 当 x2。
- [ ] 非有限值和非整数值统一归一化，不把非法值直接 cast 后消费。
- [ ] 归一化只修改字段，不自动删除或重排效果链；冲突链由第 5.2 节显式报错。

## 7. P1：移除 x2 的用户可见 `ZeroMV`

`XeSS_FrameGeneration_x2_ZeroMV.hlsl` 已声明：

```text
//!SORT_NAME XeSS Frame Generation x2
```

Overlay 已使用 `EffectDesc.sortName`，但设置页存在两个绕过点：

- `_BuildEffectMenu` 用 `effect.name` 的 basename 填 `MenuFlyoutItem.Text`。
- `ScalingModeEffectItem` 用 `EffectHelper::GetDisplayName(data.name)` 显示持久化 ID。

fix2 采用“统一用户显示名，不迁移内部 ID”的低风险方案：

- [ ] 为 `EffectInfo` 建立一个统一的 display-name helper：有 `sortName` 时取其目录后的显示部分，否则回退到持久化 ID basename。
- [ ] 添加效果菜单、已添加效果卡片和模式描述都调用该 helper。
- [ ] 用户界面统一显示 `XeSS Frame Generation x2`，不再出现 `ZeroMV`。
- [ ] 内部文件名和持久化 ID 暂时保留 `XeSSFG\XeSS_FrameGeneration_x2_ZeroMV`，避免仅为显示文字引入配置迁移和缓存双 ID。
- [ ] 不同时部署新旧两个 HLSL 名称，防止效果菜单重复。

若未来决定连内部 ID 一起改名，应另做一次单向配置迁移；不属于 fix2 的必要条件。

## 8. 运行时解析规则

- [ ] 不再用一个统一的 `std::clamp(method, 0, 2)` 解析全部 XeSSFG marker。
- [ ] 先识别 variant，再按 variant 的合法集合解析 Method、Quality、Multiplier。
- [ ] 运行时遇到超范围值时记录字段名、原值、回退值和 effect ID；不能静默变成另一个光流方法。
- [ ] `_xessMotionRequest` 每次 `Renderer::Initialize` 开始时显式重置为 None，不能继承上一次失败会话。
- [ ] 只把当前 marker 选择的 provider request 加入 Frame Guidance；MFG 永远不能构造 NVOF request。
- [ ] 日志在 SDK 初始化前打印：variant、requested multiplier、adapter vendor/device、OF method、OF quality。
- [ ] SDK properties 返回后打印：`maxSupportedInterpolations` 和最终接受的 multiplier；两者必须相同语义，不允许“requested 4x / running 2x”。
