- 官方 PDF：[NVOFA Application Note PDF](https://docs.nvidia.com/video-technologies/optical-flow-sdk/pdf/NVOFA_Application_Note.pdf)
- 编程指南：[NVIDIA Optical Flow SDK Programming Guide](https://docs.nvidia.com/video-technologies/optical-flow-sdk/nvofa-programming-guide/index.html)
- 本笔记对应：Optical Flow SDK 5.0；应用说明页面标注的最后更新时间为 2023-02-27。

## 1. 结论先行

NVOFA 是从 Turing 架构开始提供的独立硬件光流引擎。它不依赖 CUDA 核心完成主要的光流估算，因此适合在图形或计算负载运行的同时生成运动场。

对 Magpie 当前的 DLSSNR 帧引导路径，官方数据支持以下判断：

1. **优先试验 2×2 + SLOW，而不是直接采用 1×1。** 在 NVIDIA 的 KITTI 2015 测试中，更密的输出网格并不保证所有误差指标都更低；1×1 的性能代价却非常明显。
2. **Turing 只能使用 4×4 输出网格。** Ampere 和 Ada 才支持 2×2、1×1、硬件 cost 和 ROI 等完整能力。
3. **SLOW 通常质量最好，但会更多占用图形/CUDA 引擎。** 它并非“免费”的专用硬件模式。
4. **块级光流变密时的边缘处理很重要。** 单纯双线性插值会跨越物体边界混合向量；提高边缘质量不能只靠更小网格。
5. **光流无法替代真实几何运动向量与深度。** 对 DLSSNR 而言，补齐可信深度、正确的运动向量尺度/方向、遮挡处理和重置策略，可能比单独把 NVOFA 从 4×4 调到 1×1 更重要。

## 2. NVOFA 能做什么

NVOFA 接收两张图像并计算二者之间的对应关系，可工作在两种模式：

- **光流模式**：输出 X、Y 两个方向的位移。
- **立体视差模式**：输出水平方向位移；NVIDIA 文档提示此模式未来会弃用。

硬件输出是规则网格上的运动向量，每个向量代表一个像素块。可用的输出网格为：

- 4×4：每个向量覆盖 4×4 像素。
- 2×2：每个向量覆盖 2×2 像素。
- 1×1：逐像素输出。

若应用需要全分辨率运动场，可在 NVOFA 输出后进行上采样或其他后处理。需要注意：网格更密只是采样更密，不代表运动边界一定更准确。

## 5. 官方质量与性能测试的读法

### 5.1 测试条件

NVIDIA 应用说明中的光流数据使用以下环境：

- 数据集：KITTI 2015。
- 输入：1920×1080，YUV 4:2:0。
- SDK：NVIDIA Optical Flow SDK 5.0。
- 系统：Windows 11。
- 驱动：528.24 / 525.85.05。
- GPU：RTX 6000（Turing）、RTX 3090（Ampere）、RTX 4090（Ada）。
- 固定时钟：分别为 1679、1708、2114 MHz。

这些结果用于说明相对趋势，不等同于 Magpie 的 D3D11、ABGR8、桌面内容和后处理链的实际表现。

### 5.2 指标含义

- **Fl-fg**：前景像素中，平均端点误差（EPE）大于 3 的光流向量比例，单位为百分比；越低越好。
- **Fl-all**：所有像素中满足上述错误条件的比例；越低越好。
- **NOC**：只统计非遮挡区域。
- **OCC**：包含遮挡区域。
- **FPS**：只用于表达该测试环境中的处理吞吐量；不是应用端完整帧耗时。

## 10. 如何解释“更密不一定更准”

官方数据中，Ampere 的 2×2 SLOW 与 1×1 SLOW 几乎具有相同的 NOC Fl-fg（26.90 与 26.91），但吞吐量分别为 94 FPS 与 29 FPS。Ada 的 2×2 SLOW 在全部四个错误指标上都略优于 1×1 SLOW，同时吞吐量为 210 FPS，对比 1×1 的 98 FPS。

因此，至少在这组数据与实现上：

- 1×1 不是无条件的最高质量模式。
- 2×2 SLOW 是 Ampere/Ada 上更合理的高质量起点。
- 输出采样密度、匹配算法、遮挡区域、纹理特征和后处理共同决定最终质量。
- 不应仅凭网格尺寸判断 DLSSNR 的重建质量，必须做最终画面 A/B 测试。

## 11. 编程指南中的关键控制项

### 11.1 性能预设

`FAST`、`MEDIUM`、`SLOW` 在速度和质量之间取舍。SLOW 通常提供更好的向量，但 NVIDIA 明确说明它会增加图形/CUDA 引擎的使用量。因此需要测量整条渲染链，而不是只测 `nvOFExecute`。

### 11.2 输出 cost

NVOFA 可为输出向量附带 cost；cost 越高，表示该向量越不可靠。NVIDIA 推荐使用 8 位 cost。应用可利用它降低不可信区域的运动贡献，但 cost 不是几何深度，也不能独自解决遮挡。

### 11.3 正向与反向光流

同时取得前向和后向运动场后，可做 forward/backward consistency 检查。若一个像素经前向映射后，再由反向向量无法返回附近位置，通常意味着遮挡、显露、匹配错误或画面突变。这个信号适合参与置信度构造和边缘区域抑制。

### 11.4 时间提示

连续视频中，时间提示可利用前一帧结果提高估算质量；对于相互独立的图片、场景切换、窗口内容跳变或历史已失效的情况，应禁用时间提示并重建历史。

### 11.5 外部提示

外部提示具有较高优先级，只应提供质量可靠且坐标定义正确的提示。错误的游戏运动向量、颠倒的方向或错误缩放，可能比不提供提示更差。

### 11.6 向量格式

NVOFA 光流向量使用 S10.5 定点格式，即 5 位小数。读取 `R16G16_SINT` 后需要除以 32 才能得到像素单位位移，并进一步按下游 API 的坐标约定处理方向、尺度与抖动。

## 13. 对 Magpie 当前实现的对应关系

相关实现：[NvidiaOpticalFlowProvider.cpp](../src/Magpie.Core/NvidiaOpticalFlowProvider.cpp)。

当前代码的关键行为：

- 按 `{4, 2, 1}` 查询并选择第一个受支持网格，因此所有支持 4×4 的 GPU 都会优先使用 4×4。
- 固定使用 `NV_OF_PERF_LEVEL_MEDIUM`。
- 请求双向预测；若初始化失败，再退回仅前向预测。
- 启用 output cost。
- 正常连续帧启用时间提示；发生 reset 时禁用时间提示。
- 输出 `R16G16_FLOAT` 稠密运动场与 `R8_UNORM` 置信度。

这意味着当前路径实际上是**兼容性/性能优先的 4×4 MEDIUM**，并没有利用 Ampere/Ada 的 2×2 高质量甜点位。

## 14. 面向 DLSSNR 质量的建议

以下属于结合官方数据与当前代码的工程建议，不是 NVIDIA 对 Magpie 的官方结论。

### 14.1 建议的质量档位

| 档位 | Turing | Ampere / Ada | 目的 |
|---|---|---|---|
| 兼容/性能 | 4×4 MEDIUM | 4×4 MEDIUM | 保持当前性能基线 |
| 平衡 | 4×4 SLOW | 2×2 MEDIUM | 提升质量且控制额外开销 |
| 高质量 | 4×4 SLOW | 2×2 SLOW | 优先质量的推荐试验项 |
| 实验 | 不支持 | 1×1 SLOW | 仅用于对照，不建议默认启用 |

最终选择必须以 capability 查询为准，并允许初始化失败后逐级回退。

### 14.2 提高边缘质量的优先级

1. **先替换普通双线性稠密化。** 采用颜色/亮度引导的 joint bilateral upsampling、cross-bilateral 权重或简化的边缘感知邻域选择，避免前景与背景向量跨边界混合。
2. **把 cost 与双向一致性合并为置信度。** 对遮挡、显露和高 cost 区域降低运动强度，必要时回退到零运动或邻域可信运动。
3. **场景切换时强制清空历史。** 当前 reset 路径方向正确，还需保证捕获源切换、窗口尺寸变化、最小化恢复和大幅内容跳变均触发 reset。
4. **验证下游是否真正消费置信度。** 生成置信度本身不会自动提升 DLSSNR；若 NGX 接口只接收 motion/depth，需要在传入前利用置信度修正运动场或构造遮挡策略。
5. **补齐有效深度或更可靠的结构信息。** 全零深度会限制重建器判断物体前后关系的能力。若无法获得游戏深度，不要把亮度边缘伪装成物理深度；应作为低置信结构提示单独评估。

### 14.3 推荐验证矩阵

至少测试以下组合：

| 编号 | 网格/预设 | 稠密化 | 置信度处理 |
|---|---|---|---|
| A | 4×4 MEDIUM | 当前双线性 | 当前行为 |
| B | 4×4 SLOW | 当前双线性 | 当前行为 |
| C | 2×2 MEDIUM | 当前双线性 | 当前行为 |
| D | 2×2 SLOW | 当前双线性 | 当前行为 |
| E | 2×2 SLOW | 边缘感知 | cost + 双向一致性门控 |
| F | 1×1 SLOW | 最小后处理 | cost + 双向一致性门控 |

应同时记录：

- NVOFA GPU 时间、稠密化 GPU 时间和 DLSSNR 总 GPU 时间。
- 静态边缘闪烁、运动边缘拖影、显露区域破碎、细线与 HUD 稳定性。
- 场景切换后的恢复帧数。
- 不同输入帧率、缩放倍率、游戏类型以及 Turing/Ampere/Ada 的差异。

## 15. 使用这些数据时的限制

- 官方质量表来自 KITTI 道路场景，并不代表动漫、桌面文字、UI、粒子、半透明材质或快速镜头运动。
- 官方输入是 YUV 4:2:0；Magpie 当前 NVOFA 路径使用 ABGR8，输入特征会有差异。
- 固定时钟实验不代表用户机器的动态功耗、温度和并发渲染负载。
- FPS 是光流引擎吞吐量，不等于端到端帧率，也不等于 DLSSNR 的附加延迟。
- Fl 指标衡量运动估算错误比例，不直接衡量最终重建图像的主观画质。
- NVIDIA 文档的这组数字针对 SDK 5.0 与当时驱动；升级 SDK 或驱动后应重新基准测试。

## 16. 一句话决策建议

若目标是提升 Magpie 中 DLSSNR 的细节与边缘稳定性，首个实验分支应把 **Ampere/Ada 改为 2×2 SLOW、Turing 改为 4×4 SLOW**，同时保留当前配置作为回退；随后把开发重点放在**边缘感知稠密化、cost/双向一致性门控、历史重置和真实深度/结构信息**上，而不是默认追求 1×1。
